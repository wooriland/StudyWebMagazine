RAG 문서 챗봇

PDF / 문서 ↓ Embedding ↓ Vector Search ↓ Prompt Context ↓ 기존 LLM 호출
RAG의 핵심은 “새로운 지식을 모델 Weight에 다시 학습한다”가 아니라 “질문할 때 필요한 지식을 찾아 LLM에게 참고자료로 제공한다”입니다.

언제 필요한가?

최신 정보

최근 변경된 정책, 가격, 장애 대응 절차처럼 모델 학습 이후 생긴 정보

비공개 정보

사내 규정, 내부 기술문서, 개인 문서처럼 공개되지 않은 정보

전문 문서

논문, 매뉴얼, 표준서, 계약서처럼 특정 도메인의 상세한 근거

RAG가 최신 정보를 자동으로 수집하는 것은 아닙니다.

새로운 문서를 Corpus에 추가하고 Embedding·Vector Index를 갱신해야 그 정보를 검색할 수 있습니다.

RAG가 Hallucination을 100% 제거하는 것도 아닙니다.

검색 실패, 잘못된 Chunk, 문서 자체의 오류, Prompt 문제, LLM의 Context 오해가 남을 수 있습니다. RAG는 문서 근거를 제공해 근거 기반 답변 가능성을 높이는 구조입니다.

07 · SHAPE / DATA STRUCTURE

Shape 흐름 — Sequence Tensor에서 Vector Matrix로

이번 단원에서는 `(batch, timestep, feature)`보다 문서 Chunk 수 N과 Embedding Dimension d가 중요합니다.

PDF Pages
P개 ↓ Document Chunks
N개 ↓ Chunk Embeddings
(N,d) ↔ Query Embedding
(d,) ↓ Top-k Documents
최대 3개
데이터 개념 구조 원본 저장 여부
Page Documents P개 개수 출력 없음
Chunk Documents N개 목록은 출력됨
Document Embeddings (N,d) Shape 출력 없음
Query Embedding (d,) Shape 출력 없음
Retrieved Documents Top-k, 원본 k=3 질의 결과 저장 없음
Embedding Dimension d는 원본에서 출력하지 않습니다.

사용한 모델 이름은 text-embedding-3-small이지만, Notebook에는 실제 Vector Shape 출력이 없습니다. 따라서 학습 자료에서는 d로 표현하고 원본이 제시하지 않은 숫자를 임의로 삽입하지 않습니다.

08 · DOCUMENT PREPROCESSING

전처리 — PDF를 검색 가능한 Chunk로 만들기

  1. PDF Load PyPDFLoader로 Page Document 생성
  2. Chunk Split 긴 Page를 검색 가능한 작은 단위로 분할
  3. Overlap Chunk 경계의 문맥 단절을 줄이기 위해 일부 내용 반복
  4. Embedding 각 Chunk를 Vector로 변환
  5. Vector Index FAISS에 검색 가능한 형태로 저장
원본 코드 · PDF Load → Chunk Split 
# 1. PDF 로드
loader = PyPDFLoader(
    "data/company_policy_rag.pdf"
)

pages = loader.load()


# 2. 텍스트 분할
splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=100
)

docs = splitter.split_documents(
    pages
)

print(docs)
무엇?
PDF를 읽고 Page를 작은 Chunk로 분리합니다.
왜?
질문과 관련된 문서 일부만 검색하기 위해서입니다.
입력
PDF File
출력
List[Document] 형태의 Chunk 목록

Chunk Size = 500

원본의 500은 한 Chunk의 목표 문자 길이 규모입니다. 모든 문서에서 최적이라는 의미는 아닙니다.

Chunk Overlap = 100

Chunk A 앞 내용 · 핵심 문장 · 경계 문맥
Chunk B 경계 문맥 · 다음 내용 · 다음 문단

의미가 Chunk 경계에서 완전히 끊어지는 문제를 줄이는 역할을 합니다.

RecursiveCharacterTextSplitter와 Semantic Chunking은 같지 않습니다.

교안은 의미 단위 분할의 필요성을 설명하지만, 실제 사용 클래스는 문자 기반 경계를 재귀적으로 찾는 Text Splitter입니다. 문서 의미를 완벽하게 이해해 자동 분할한다고 설명하지 않습니다.

09 · EMBEDDING / VECTOR STORE

Embedding과 FAISS — 문장의 의미를 검색 가능한 좌표로

원본 Embedding / FAISS Cell 008 
embeddings = OpenAIEmbeddings(
    model="text-embedding-3-small"
)

vectordb = FAISS.from_documents(
    docs,
    embeddings
)

Embedding

“Sev1 장애는 전체 서비스 중단을 의미한다.”
↓
[v₁, v₂, v₃, ..., vd]

텍스트를 의미 비교가 가능한 수치 Vector로 바꿉니다.

FAISS

docs + embeddings → FAISS.from_documents(...) → Vector Search Index
무엇?
모든 Chunk의 Embedding을 계산하고 검색 Index를 구성합니다.
왜?
Query와 의미적으로 가까운 Chunk를 빠르게 찾기 위해서입니다.
개념 Shape
N개의 Chunk → `(N,d)`
상태 변화
검색 가능한 Vector Store가 메모리에 생성됩니다.
FAISS.from_documents()는 model.fit()이 아닙니다.

정답과 예측을 비교해 Loss를 최소화하거나 Model Weight를 Gradient로 업데이트하지 않습니다. Embedding 계산과 검색 Index 구축 과정입니다.

원본 핵심 예제에는 Vector DB 영구 저장이 없습니다.

save_local()과 같은 영구 저장 코드는 이 기본 RAG Cell에 포함되어 있지 않습니다. Notebook 재시작 후 Index를 자동 복원한다고 가정하지 않습니다.

10 · RETRIEVAL

Retriever — 질문과 가까운 Chunk Top-3 찾기 

retriever = vectordb.as_retriever(
    search_kwargs={
        "k": 3
    }
)
Question “Sev1은 무엇인가요?”
↓
Query Embedding (d,)
↓
FAISS N Document Vectors
↓
Top-3 Documents

k가 크면 무조건 좋은가?

큰 k

정답 근거를 포함할 가능성이 늘지만 Noise와 Prompt 길이도 증가할 수 있습니다.

작은 k

Context는 간결하지만 필요한 근거를 놓칠 수 있습니다.

검색 Metric을 원본에서 임의로 Cosine이라고 확정하지 않습니다.

원본은 Vector Search를 구성하지만 별도의 Distance Strategy를 코드에서 지정하지 않습니다. 따라서 이 페이지에서는 “Embedding 기반 유사 문서 검색”으로 표현합니다.

보충 진단 · 검색된 Chunk 직접 확인 
# 원본에 없는 디버깅 예제입니다.

retrieved_docs = retriever.invoke(
    "Sev1은 무엇인가요?"
)

for index, doc in enumerate(
    retrieved_docs,
    start=1
):
    print(
        f"--- Result {index} ---"
    )

    print(
        doc.metadata
    )

    print(
        doc.page_content
    )

답변이 틀렸을 때 LLM을 먼저 바꾸기보다, Retriever가 실제로 어떤 문서를 가져왔는지 확인합니다.

11 · PROMPT / LCEL

검색 문서와 질문을 LLM 입력으로 연결하기

Prompt의 역할

RAG에서는 검색된 Chunk를 그대로 가져오는 것만으로 끝나지 않습니다. LLM에게 어떤 자료를 참고하고, 문서에 정보가 없을 때 어떻게 행동할지도 알려줘야 합니다.

기업 내부 지식 지원 센터 AI

  • 제공된 참고 문서에 명시된 내용만 답변

def format_docs(
    docs
):
    return "\n\n".join(
        (
            "[source="
            f"{doc.metadata.get('source')}, "
            "page="
            f"{doc.metadata.get('page')}]\n"
            f"{doc.page_content}"
        )
        for doc in docs
    )

원본을 수정한 코드가 아니라 출처·페이지 추적을 쉽게 만들기 위한 별도 확장 예제입니다.

대신 무엇을 하는가?

문서 ↓ Chunk ↓ Embedding ↓ FAISS Index 구축

정답과 Prediction의 Loss를 계산하거나 Backpropagation으로 Model Weight를 변경하지 않습니다. 문서 Vector를 생성하고 검색 가능한 Index를 구성합니다.

Data Leakage는 어떻게 달라지는가?

전통적인 Train/Validation 누수는 이번 핵심 이슈가 아닙니다. 하지만 평가용 질문과 정답이 검색 Corpus에 그대로 들어 있다면 현실적인 Retrieval 능력을 과대평가할 수 있습니다.

보충 개념 · Evaluation Leakage

Benchmark Q/A 자체를 검색 문서에 그대로 넣어 놓고 “Retriever가 정답을 잘 찾았다”고 평가하면 실제 문서 검색 성능을 과대평가할 수 있습니다.

20 · COMMON MISTAKES

자주 하는 실수 — 딥러닝 학습 개념을 RAG에 억지로 적용하지 않기

실수 정확한 이해
FAISS.from_documents()가 fit이다 Embedding 계산 + Vector Index 구축
RAG와 Fine-tuning은 같다 Weight 변경과 Context 검색은 다름
RAG면 최신 정보가 자동 반영된다 Corpus와 Index가 갱신되어야 함
RAG면 Hallucination이 사라진다 검색·Prompt·문서 오류 가능성이 남음
500 / 100은 최적 공식이다 문서 종류별로 실험할 Hyperparameter
Recursive Splitter = Semantic Chunking 같은 개념이 아님
k는 클수록 좋다 Recall과 Noise의 Trade-off
Vector Search는 무조건 Cosine이다 원본에 특정 Distance Strategy 설정 없음
print(docs)는 RAG 답변이다 Chunk Document 목록 출력
질의 코드가 있으니 답도 실행됐다 질의 Cell의 저장 출력은 없음
session_state = LLM Memory 원본은 UI History만 저장
현재 PDF 코드와 저장 출력은 같은 실행이다 Source가 서로 달라 실행 이력 확인 필요

Data Leakage

전통적인 Train/Validation Leakage보다 RAG 평가 Corpus의 오염을 생각하는 편이 적절합니다.

평가 Question 우리 회사 연차는 몇 일인가요?

Corpus 안 Q: 우리 회사 연차는 몇 일인가요? A: 15일

Benchmark Q/A를 문서에 그대로 넣어 놓고 검색 성능이 좋다고 평가하면 실제 문서 Retrieval 능력을 과대평가할 수 있습니다.

  1. 문서 Coverage 확인 질문에 답할 정보가 Corpus 자체에 존재하는지 먼저 확인합니다.
  2. PDF Parsing 품질 표·머리글·페이지 구성이 제대로 Text로 추출되는지 봅니다.
  3. Chunk 전략 문서 종류에 맞게 Size와 Overlap을 조정합니다.
  4. Embedding 일관성 Index와 Query가 같은 Embedding 공간을 사용하도록 합니다.
  5. Top-k 비교 Recall과 Noise 사이의 균형을 실험합니다.
  6. Retrieved Context 관찰 LLM 이전에 검색 문서가 맞는지 직접 확인합니다.
  7. Prompt 정책 문서에 없는 내용은 추측하지 않도록 명확하게 지시합니다.
  8. Metadata / Citation 문서 이름·페이지·버전을 답변 근거와 연결합니다.
  9. 평가 Set 질문·기대 근거·Reference Answer를 별도로 준비합니다.
  10. Latency / Cost Embedding·검색·LLM 호출 비용과 시간을 함께 측정합니다.

Chunk Size / k는 모델 Hyperparameter처럼 실험한다

Chunk가 너무 작음

필요한 문맥이 여러 Chunk로 잘려 답변 근거가 부족할 수 있습니다.

Chunk가 너무 큼

관련 없는 문장이 함께 포함되어 검색 정밀도가 떨어질 수 있습니다.

k가 너무 작음

필요한 근거를 놓칠 수 있습니다.

k가 너무 큼

Noise와 Context 길이·비용이 증가할 수 있습니다.

이번 단원의 “튜닝”은 Learning Rate 튜닝과 다릅니다.

모델 Weight를 최적화하는 것이 아니라 Corpus, Chunking, Retrieval, Prompt, Context 구성과 운영 설정을 개선합니다.

실무 연결 — RAG를 서비스로 운영한다면

두 서비스로 분리해서 생각하기

Document Ingestion Service

문서 업로드 ↓ Parsing ↓ Chunk ↓ Embedding ↓ Vector Store Update

Query Service

User Question ↓ Retriever ↓ Context ↓ LLM ↓ Answer

문서 Metadata

실무에서는 단순 본문뿐 아니라 다음 정보도 중요합니다.

source page title section version effective_date department

문서 Version

2025 규정 연차 14일
↔
2026 규정 연차 15일

여러 Version이 동시에 Vector Store에 있으면 오래된 규정과 최신 규정이 함께 검색될 수 있습니다. Metadata Filter와 Version 정책이 중요합니다.

접근 권한

사내 RAG는 권한 필터가 필요합니다.

모든 사용자가 모든 문서를 검색할 수 있게 하면 인사·보안·계약 문서가 잘못 노출될 수 있습니다. 사용자 권한에 따라 검색 가능한 Corpus를 제한하는 구조가 필요합니다.

실무 RAG 운영 흐름

  1. 문서 등록 Version과 접근 권한을 Metadata에 기록
  2. Parsing / Chunking 표·문단·제목 구조를 가능한 한 보존
  3. Embedding / Indexing Vector Store 갱신
  4. Retrieval Logging 질문마다 검색된 Chunk와 Score를 기록
  5. Generation 문서 Context와 질문을 LLM에 전달
  6. Citation 답변에 근거 문서·페이지 표시
  7. Feedback / Evaluation 검색 실패와 답변 오류를 수집

24 · INTERVIEW / REVIEW

면접 포인트와 복습 질문

답을 먼저 보지 말고 Document → Retrieval → Generation 순서로 설명해 보세요.

Q01. RAG란 무엇입니까?

외부 정보 Retrieval과 LLM Generation을 결합해, 검색된 문서를 Context로 제공한 뒤 문서 근거 기반 답변을 생성하는 구조입니다.

Q02. RAG와 Fine-tuning은 어떻게 다릅니까?

Fine-tuning은 Model Weight를 변경하지만, RAG는 외부 문서를 검색하여 Prompt Context로 제공합니다.

Q03. RAG가 최신 정보를 활용할 수 있는 이유는 무엇입니까?

새 문서를 Corpus와 Vector Index에 반영하면 모델 자체를 다시 학습하지 않고도 검색 Context로 사용할 수 있기 때문입니다.

Q04. 새 문서가 생기면 RAG가 자동으로 아는 것입니까?

아닙니다. 문서를 Chunk하고 Embedding하여 Index에 반영해야 검색 가능합니다.

Q05. Chunking을 왜 합니까?

긴 문서 전체 대신 질문과 관련된 작은 문서 조각을 검색하기 위해서입니다.

Q06. chunk_overlap의 역할은 무엇입니까?

Chunk 경계에서 문맥이 완전히 끊기는 문제를 줄이기 위해 일부 내용을 다음 Chunk에 반복합니다.

Q07. 이번 원본 Chunk 설정은 무엇입니까?

chunk_size=500, chunk_overlap=100입니다.

Q08. Embedding이란 무엇입니까?

텍스트의 의미적 특징을 비교 가능한 숫자 Vector로 표현하는 방식입니다.

Q09. 이번 실습의 Vector Store는 무엇입니까?

FAISS입니다.

Q10. Retriever는 무엇을 합니까?

질문과 의미적으로 가까운 Document Chunk를 Vector Store에서 검색합니다.

Q11. 원본 Retriever의 k는 얼마입니까?

3입니다. 상위 세 개의 관련 Chunk를 검색하도록 설정합니다.

Q12. k는 클수록 항상 좋습니까?

아닙니다. 관련 문서 Recall은 높아질 수 있지만 Noise와 Prompt 길이·비용도 증가할 수 있습니다.

Q13. 이번 Notebook에서 Loss는 무엇입니까?

없습니다. LLM Weight를 새로 학습하지 않습니다.

Q14. Optimizer는 무엇입니까?

없습니다. Backpropagation이나 Weight Update를 수행하지 않습니다.

Q15. FAISS.from_documents()는 fit()입니까?

아닙니다. Document Embedding을 만들고 Vector 검색 Index를 구축합니다.

Q16. RAG에서 X와 y는 무엇입니까?

전통적인 supervised X_train/y_train은 없습니다. 사용자 Query가 입력이며, 답변은 검색 Context를 이용해 LLM이 생성합니다.

Q17. Embedding의 Shape은 어떻게 이해합니까?

N개의 Chunk와 d차원 Embedding이라면 Document Matrix는 개념적으로 (N,d), Query Vector는 (d,)입니다. 원본 Notebook은 d를 실제 출력하지 않습니다.

Q18. RAG면 Hallucination이 사라집니까?

아닙니다. 검색 실패, 잘못된 문서, Prompt 오류, 문서 해석 오류 등이 남을 수 있습니다.

Q19. 답변이 틀렸을 때 가장 먼저 무엇을 확인합니까?

Retriever가 올바른 Chunk를 가져왔는지 확인합니다. Context가 맞으면 그 다음 Prompt와 Generation을 봅니다.

Q20. 원본에서 실제 RAG Answer가 저장되어 있습니까?

없습니다. 저장된 한 개의 출력은 print(docs)의 Document Chunk 목록입니다.

Q21. 코드와 저장 출력의 PDF Source에서 주의할 점은 무엇입니까?

현재 코드는 company_policy_rag.pdf를 읽지만, 저장 metadata는 Samsung_Card_Manual_Korean_1.3.pdf를 가리킵니다. 실행 이력을 현재 자료만으로 단정하지 않습니다.

Q22. RunnablePassthrough는 무엇을 합니까?

입력 질문을 그대로 Prompt의 question 값으로 전달합니다. 같은 입력은 Retriever가 context를 만드는 데도 사용합니다.

Q23. 기본 RAG Chain과 Streamlit Chain의 출력 차이는 무엇입니까?

기본 Chain은 AIMessage 형태를 반환해 answer.content를 사용하고, Streamlit 확장에서는 StrOutputParser를 통해 문자열을 반환하도록 구성할 수 있습니다.

Q24. st.session_state.messages는 LLM Memory입니까?

원본 코드에서는 UI에 이전 메시지를 저장·표시하지만, rag_chain에는 현재 질문만 전달하므로 그 자체가 Multi-turn LLM Memory는 아닙니다.

Q25. 다음 단원은 무엇입니까?

ML 65. LangChain 문서 챗봇 구현입니다. Loader, Vector Store, Retriever, Memory, Streamlit을 더 체계적으로 연결합니다.

복습 완료 기준

PDF → Chunk → Embedding → FAISS → Retriever → Context → Prompt → LLM → Answer를 설명하고, Loss·Optimizer·fit이 없는 이유와 Retrieval / Generation 평가를 분리해서 설명할 수 있어야 합니다.
