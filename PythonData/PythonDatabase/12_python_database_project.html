    _id INTEGER
        PRIMARY KEY
        AUTOINCREMENT,

    name TEXT
        NOT NULL,

    tel TEXT
        NOT NULL
        DEFAULT 'unknown',

def save(
    conn,
    name,
    tel
):

    sql = """
    INSERT INTO Member(
        name,

≠
SERVICE Business Operation

회원 등록 Service

def create_member(
    repository,
    name,
    tel
):

    if not name.strip():

        raise ValueError(
            "이름을 입력하세요."
        )


    if len(tel.strip()) < 3:

        raise ValueError(
            "전화번호가 너무 짧습니다."
        )


    conn = None


    try:

        conn = get_connection()


        member_id = repository.save(
            conn,
            name,
            tel
        )


        conn.commit()


        return member_id


    except Exception:

        if conn is not None:
            conn.rollback()


        raise


    finally:

        if conn is not None:
            conn.close()

            elif choice == "0":

                print(
                    "프로그램을 종료합니다."
                )

                break


            else:

                print(
                    "올바른 메뉴를 선택하세요."
                )


        except ValueError as error:

            print(
                "입력 오류:",
                error
            )


        except Exception as error:

            print(
                "Database 작업 실패:",
                error
            )

Beginner Mistakes

종합 프로젝트에서 자주 하는 실수

01

모든 코드를 app.py에 작성한다.

Connection·SQL·Transaction·UI 책임이 뒤섞입니다.

02

Repository와 Service를 같은 Layer로 생각한다.

Database Operation과 Business Operation을 구분합니다.

03

Repository마다 commit한다.

여러 SQL이 하나의 Business Transaction인지 먼저 확인합니다.

04

외부 입력을 SQL 문자열에 직접 결합한다.

Parameterized Query를 사용합니다.

05

SQLite의 ?와 PyMySQL의 %s를 혼동한다.

Driver별 Placeholder를 확인합니다.

06

Parameter Query만 사용하면 모든 보안이 해결된다고 생각한다.

Secret·Privilege·Network도 별도 문제입니다.

07

Password를 config.py에 Literal로 옮기고 안전하다고 생각한다.

실제 Secret은 Source Repository 밖으로 분리합니다.

08

Connection과 Cursor를 같은 객체로 생각한다.

연결·Transaction과 SQL·Result 책임을 구분합니다.

09

SELECT에도 습관적으로 commit을 붙인다.

Read와 Data 변경 작업을 구분합니다.

10

DML 후 commit을 잊는다.

실행과 변경 확정은 다른 단계입니다.

11

실패했는데 rollback을 하지 않는다.

업무 단위의 미확정 변경을 취소해야 할 수 있습니다.

12

close를 저장 명령으로 생각한다.

commit과 close는 서로 다른 책임입니다.

13

오류 발생 시 Resource가 자동 정리된다고 생각한다.

finally 또는 Context Manager 구조를 사용합니다.

14

affected == 0을 SQL Error라고 생각한다.

조건에 맞는 Row가 없을 수 있습니다.

15

fetchone()의 None을 Exception이라고 생각한다.

조회 결과가 없다는 정상적인 상태일 수 있습니다.

16

UPDATE·DELETE에서 WHERE를 빠뜨린다.

많은 Row가 변경될 수 있어 가장 주의해야 합니다.

17

SQLite File Path를 확인하지 않는다.

CWD가 달라지면 예상하지 못한 DB File을 열 수 있습니다.

18

MySQL Server 문제를 SQL 문제로 생각한다.

Connection이 안 됐다면 SQL까지 도달하지 않았습니다.

19

Access denied에서 Password만 확인한다.

User·Host·Password·Privilege를 구분합니다.

20

SQLite와 MySQL SQL을 무조건 하나로 합치려 한다.

공통 개념과 DBMS별 문법 차이를 구분합니다.

21

모든 함수마다 DBMS if문을 작성한다.

DBMS 차이를 Connection/Repository에 집중시키는 것이 좋습니다.

22

Exception을 except Exception: pass로 숨긴다.

정리 후 필요한 상위 Layer에 오류를 전달합니다.

Interview Point

프로젝트를 설명할 수 있어야 진짜 이해한 것이다

Q1. 이번 CRUD 프로젝트의 핵심 목적은 무엇인가요?
A.

SQLite와 MySQL CRUD를 구현하면서 Connection, Parameter Query, Transaction, Error Handling, Repository와 Service의 책임을 하나의 Application 구조로 종합하는 것입니다.

Q2. Repository는 어떤 역할을 하나요?
A.

SQL 작성, Parameter Binding, execute와 fetch 같은 Database 접근 책임을 담당합니다.

Q3. Service는 어떤 역할을 하나요?
A.

입력값 검증, Business Logic, 여러 Repository 작업의 조합, Transaction Boundary를 담당할 수 있습니다.

Q4. Repository와 Service의 차이는 무엇인가요?
A.

Repository는 Database Operation, Service는 Business Operation을 담당합니다.

Q5. SQLite와 MySQL의 가장 큰 구조적 차이는 무엇인가요?
A.

SQLite는 File 기반 Embedded Database이고, MySQL은 별도의 Server에 접속하는 Client-Server Database입니다.

Q6. SQLite와 MySQL의 Placeholder는 어떻게 다른가요?
A.

sqlite3에서는 대표적으로 ?, PyMySQL에서는 %s를 사용합니다.

Q7. Oracle까지 비교하면 어떤가요?
A.

Oracle Driver에서는 :name 같은 Bind Variable을 사용할 수 있습니다. Parameter Binding의 목적은 동일하지만 Driver별 표기가 다릅니다.

Q8. Parameterized Query를 사용하는 이유는 무엇인가요?
A.

외부 입력을 SQL 문자열과 직접 결합하지 않고 Driver Parameter로 전달하여 SQL Code와 Data를 분리하기 위해서입니다.

Q9. Connection과 Cursor의 역할 차이는 무엇인가요?
A.

Connection은 Database 연결과 Transaction, Cursor는 SQL 실행과 조회 Result 처리를 담당합니다.

Q10. SELECT와 DML의 후속 흐름은 어떻게 다른가요?
A.

SELECT는 execute 이후 fetch로 결과를 가져오고, INSERT·UPDATE·DELETE는 변경 결과에 따라 commit 또는 rollback을 고려합니다.

Q11. Transaction Boundary란 무엇인가요?
A.

여러 Database 작업 중 어디까지를 하나의 업무 단위로 함께 확정하거나 취소할지 정하는 경계입니다.

Q12. Repository 안에서 항상 commit하면 안 되는 이유는 무엇인가요?
A.

하나의 Business Transaction이 여러 Repository 작업으로 구성될 수 있기 때문입니다. 중간 Repository가 먼저 Commit하면 이후 작업 실패 시 전체 Rollback이 어려워질 수 있습니다.

Q13. commit과 rollback의 차이는 무엇인가요?
A.

commit은 미확정 변경을 확정하고, rollback은 미확정 변경을 취소합니다.

Q14. commit과 close는 같은가요?
A.

아닙니다. commit은 Transaction, close는 Resource 종료입니다.

Q15. Auto Commit과 Manual Transaction은 어떻게 다른가요?
A.

Auto Commit은 변경의 자동 확정 방식과 연결되고, Manual Transaction에서는 Application이 명시적으로 commit과 rollback 시점을 결정합니다.

Q16. 왜 Password를 Source Code와 분리하나요?
A.

Git이나 Source 공유 과정에서 Credential이 노출되는 위험을 줄이고, 개발·테스트·운영 환경별 설정을 분리하기 위해서입니다.

Q17. affected rows가 0이면 SQL Error인가요?
A.

반드시 그렇지는 않습니다. SQL은 정상 실행됐지만 WHERE 조건에 해당하는 Row가 없을 수 있습니다.

Q18. fetchone()이 None이면 오류인가요?
A.

아닙니다. 조회 조건과 일치하는 Row가 없다는 정상적인 Application 상태일 수 있습니다.

Q19. DBMS가 바뀔 때 프로젝트 어디가 주로 변경되어야 하나요?
A.

잘 분리된 구조라면 Connection, Repository SQL, Placeholder, Result Mapping 같은 Database Layer를 중심으로 변경할 수 있습니다.

Q20. Database Code를 추상화한다는 것을 초보자 기준으로 설명해 보세요.
A.

app.py가 sqlite3.connect()나 pymysql.connect()를 직접 알지 않게 하고, SQL은 Repository에 분리하여 Database 세부 구현이 Application 전체로 퍼지지 않게 만드는 것부터 시작할 수 있습니다.

Q21. Database 오류는 어떤 순서로 확인하나요?
A.

Input → Python → Configuration → Driver → Connection → Authentication/Privilege → Database/Table → Binding → SQL → Constraint → Transaction 순으로 오류 계층을 좁혀 확인합니다.

Q22. Crawling과 이번 Database Project는 어떻게 연결되나요?
A.

Crawling한 데이터를 정제한 뒤 Repository에서 Parameterized INSERT 또는 executemany()로 SQLite나 MySQL에 저장하는 구조로 연결할 수 있습니다.

Q23. Database와 Data Analysis는 어떻게 연결되나요?
A.

Database에서 SELECT한 데이터를 Python으로 가져와 Pandas DataFrame으로 만들고 이후 shape, dtype, 결측치, groupby 등의 분석 단계로 연결할 수 있습니다.

Confusing Point

헷갈리기 쉬운 개념

Application ≠ Repository

사용자 흐름과 SQL 책임을 구분합니다.

Repository ≠ Service

Database Operation과 Business Operation을 구분합니다.

Connection ≠ Cursor

연결·Transaction과 SQL·Result 역할을 구분합니다.

SQL Code ≠ External Data

외부 값은 Parameter Binding으로 전달합니다.

config.py ≠ Secret Store

실제 Password Literal을 config.py로 옮기는 것만으로는 Source Code 분리가 아닙니다.

SQLite ? ≠ PyMySQL %s

Parameter Binding 목적은 같지만 Driver 문법이 다릅니다.

execute 성공 ≠ commit 완료

SQL 실행과 Transaction 확정을 구분합니다.

commit ≠ close

변경 확정과 Resource 종료입니다.

affected = 0 ≠ SQL Error

조건에 맞는 Row가 없는 정상 실행일 수 있습니다.

fetchone() None ≠ Exception

조회 결과 없음 상태일 수 있습니다.

Auto Commit ≠ 무조건 나쁨

현재 Transaction Mode와 업무 경계를 알고 선택해야 합니다.

Context Manager ≠ Transaction

Resource 관리와 변경 확정은 다른 책임입니다.

SQLite ≠ 하위 버전 MySQL

규모와 운영 환경에 따라 서로 다른 목적을 가진 DBMS입니다.
