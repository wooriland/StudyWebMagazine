Python Database · Lesson 09

MySQL 사용자와 권한 User · Host · GRANT · Privilege · Least Privilege

MySQL Server에 접속할 수 있다는 것과 모든 SQL을 실행할 수 있다는 것은 같은 의미가 아닙니다. MySQL에서는 Account를 User와 접속 Host의 조합으로 이해하고, Account가 어떤 Database·Table에서 SELECT·INSERT·UPDATE·DELETE 같은 작업을 수행할 수 있는지 Privilege로 관리합니다. 이번 단원에서는 CREATE USER, GRANT, ALTER USER, DROP USER를 중심으로 최소 권한 원칙과 실제 Application Account 설계까지 연결합니다.

Client → User@Host → Authentication → Privilege → Database / Table → SQL
ADMIN root
  • Server 관리
  • User 생성
  • Privilege 관리
≠
APPLICATION app_user
  • 필요한 Database만
  • 필요한 SQL만
  • 최소 권한

학습 목표

  • MySQL에서 User와 Privilege가 필요한 이유를 설명할 수 있다.
  • root와 Application User의 역할을 구분할 수 있다.
  • MySQL Account를 'user'@'host' 구조로 읽을 수 있다.
  • 같은 User 이름이라도 Host가 다르면 다른 접속 조건으로 이해할 수 있다.
  • 접속 가능 여부와 SQL 실행 가능 여부를 구분할 수 있다.
  • CREATE USER와 GRANT의 역할을 구분할 수 있다.
  • SELECT·INSERT·UPDATE·DELETE 등 주요 Privilege를 설명할 수 있다.
  • *.*, database.*, database.table의 권한 범위를 구분할 수 있다.
  • 최소 권한 원칙이 무엇인지 설명할 수 있다.
  • SHOW GRANTS로 실제 Account 권한을 확인할 수 있다.
  • REVOKE와 DROP USER의 차이를 설명할 수 있다.
  • ALTER USER로 Account의 비밀번호를 변경하는 흐름을 이해한다.
  • localhost·특정 Host·넓은 Host 범위의 차이를 이해한다.
  • 교안의 FLUSH PRIVILEGES 설명과 Step 1·2 보완 내용을 구분한다.
  • Access denied 오류를 User·Host·Password·Privilege 관점에서 읽을 수 있다.
  • Database Password를 Source Code와 분리해야 하는 이유를 설명할 수 있다.
  • SQL Injection 방지를 위해 Parameterized Query를 계속 사용해야 함을 이해한다.

  • 다음 PyMySQL 연동 단원에서 Application Account를 실제 Connection에 사용할 준비를 한다.
01

Core Concept

모든 사용자가 모든 SQL을 실행하게 두지 않는다

MySQL Server에는 관리자, Backend Application, 분석 프로그램, Batch 프로그램처럼 서로 다른 목적의 Client가 접속할 수 있습니다. 이들이 모두 root와 같은 권한을 가질 필요는 없습니다.

DB ADMIN 관리자
  • User 생성
  • 권한 관리
  • Schema 관리
BACKEND Application
  • SELECT
  • INSERT
  • UPDATE
  • DELETE
REPORT 분석 / Report
  • SELECT 중심
  • 읽기 전용 가능
BATCH 수집 / Batch
  • SELECT
  • INSERT
WHO? 누가?
FROM WHERE? 어디에서?
WHAT? 무엇을?
WHERE? 어느 DB/Table에서?
권한은 “User가 있느냐?”만의 문제가 아니다.

누가, 어디에서 접속해서, 어떤 Database·Table에 어떤 Operation을 수행할 수 있는지까지 함께 봅니다.

Host Scope

localhost · 특정 Host · 넓은 Host 범위

LOCAL 'app_user'@'localhost'

MySQL Server가 있는 로컬 환경의 접속과 연결합니다.

SPECIFIC HOST 'app_user'@'192.168.10.20'

특정 Application Server나 접속 위치를 명시하는 방향입니다.

교안의 넓은 범위 'app_user'@'%'

첨부 교안에서는 모든 Host에서 접속을 허용하는 예로 설명합니다.

Step 1·2 보완

넓은 Host 범위를 편의상 기본값으로 사용하기보다 실제 Application이 어디에서 접속해야 하는지 먼저 정한 뒤 필요한 범위로 제한하는 방향을 학습합니다.

Account Host + Server Bind + Network + Firewall
MySQL Account의 Host 제한 = Network 보안 전체는 아니다.
13

Source vs Supplement

FLUSH PRIVILEGES — 교안 내용과 보완 내용을 구분한다

첨부 교안 
GRANT ALL PRIVILEGES
ON sampledb.*
TO 'sample'@'localhost';


FLUSH PRIVILEGES;
권한 설정 적용

교안에서는 GRANT 다음에 FLUSH PRIVILEGES를 실행하는 흐름으로 설명합니다.

Step 1·2 보완
CREATE USER GRANT REVOKE ALTER USER ↓ 일반 Account 관리 흐름

이번 과정에서는 모든 GRANT 뒤에 FLUSH PRIVILEGES를 반드시 붙이는 암기 공식으로 사용하지 않습니다.

교안 원문을 삭제하지 않고 “교안 기준 / 보완 기준”으로 분리한다.

원문의 학습 흐름은 보존하면서 Step 1·2에서 정리한 현재 관리 방식과 구분해서 기억합니다.

Parameterized SQL

최소 권한과 SQL Injection 방지는 서로 다른 보안 계층이다

SQL LAYER Parameterized Query

외부 Data를 SQL Code와 직접 문자열로 합치지 않습니다.

WHERE name = %s
ACCOUNT LAYER Least Privilege

Account가 실행할 수 있는 Operation과 Scope를 제한합니다.

GRANT SELECT, INSERT ...
Parameter Binding ≠ Privilege

피해야 할 Application 코드

name = input("이름: ")


sql = f"""
SELECT *
FROM Member
WHERE name = '{name}'
"""

PyMySQL Parameter 방향

sql = """
SELECT *
FROM Member
WHERE name = %s
"""


cursor.execute(
    sql,
    (name,)
)
User Input → Parameter Binding → app_user → Privilege Check → Database

  6. Login 자체는 성공했는가?
  7. 실행하려는 SQL의 Privilege가 있는가?
  8. Privilege가 올바른 Database Scope에 있는가?
  9. Table Scope가 맞는가?
  10. 그 다음 SQL Syntax와 Constraint를 확인한다.
  11. 변경 작업이면 Transaction 상태도 확인한다.

관리 계정과 Application 전용 Account를 구분합니다.

User 이름 하나만 MySQL Account라고 생각한다.

User + Host 조합으로 읽습니다.

03

app_user@localhost와 다른 Host의 Account를 구분합니다.

04

CREATE USER만 하면 CRUD도 가능하다고 생각한다.

Account 생성과 Privilege 부여는 별도 단계입니다.

Interview Point

면접에서 설명할 수 있어야 하는 질문

Q1. MySQL Account는 어떻게 이해하면 되나요?
A.

User Name만 보는 것이 아니라 User와 접속 Host의 조합으로 이해합니다. 대표적인 표현은 'app_user'@'localhost'입니다.

Q2. 같은 User 이름이면 항상 같은 Account인가요?
A.

Host 조건이 다르면 서로 다른 접속 Account로 구분해서 이해해야 합니다.

Q3. CREATE USER와 GRANT의 차이는 무엇인가요?
A.

CREATE USER는 Account를 만들고, GRANT는 Account에 Database 작업 권한을 부여합니다.

Q4. 최소 권한 원칙이란 무엇인가요?
A.

Account에 업무 수행에 실제 필요한 Operation과 Object Scope만 허용하는 원칙입니다.

Q5. ALL PRIVILEGES를 항상 사용하지 않는 이유는 무엇인가요?
A.

Application에 필요하지 않은 작업까지 수행할 수 있게 되어 권한 범위가 불필요하게 커질 수 있기 때문입니다.

Q6. *.*, db.*, db.table의 차이는 무엇인가요?
A.

각각 Global, Database, 특정 Table 수준의 권한 Scope로 이해할 수 있습니다.

Q7. SHOW GRANTS는 왜 사용하나요?
A.

Account에 실제 어떤 Privilege가 어느 범위로 설정되었는지 검증하기 위해 사용합니다.

Q8. REVOKE는 무엇인가요?
A.

이미 부여된 특정 Privilege를 Account에서 제거할 때 사용합니다.

Q9. REVOKE와 DROP USER는 어떻게 다른가요?
A.

REVOKE는 Account를 유지하면서 권한을 제거하고, DROP USER는 Account 자체를 삭제합니다.

Q10. ALTER USER는 언제 사용하나요?
A.

기존 Account의 Password 같은 Account 설정을 변경할 때 사용합니다.

Q11. localhost는 무엇을 의미하나요?
A.

해당 MySQL Account의 접속 Host 조건을 Local Host로 설정한 형태로 이해합니다.

Q12. Login 성공과 SQL 실행 가능은 같은 의미인가요?
A.

아닙니다. 접속 인증에 성공한 뒤에도 실행하는 SQL마다 필요한 Privilege가 있는지 확인해야 합니다.

Q13. Login은 되는데 SELECT가 실패하면 무엇을 확인하나요?
A.

SELECT Privilege와 Database·Table Scope가 올바른지 확인합니다. Step 1·2에서는 SHOW GRANTS를 이용해 검증하는 흐름으로 정리했습니다.

Q14. FLUSH PRIVILEGES는 GRANT 뒤 항상 필요한가요?
A.

첨부 교안에는 GRANT 뒤 FLUSH PRIVILEGES를 실행하는 흐름이 제시됩니다. 이번 과정에서는 이 내용을 보존하되, Step 1·2에서 정리한 보완 내용과 구분해서 학습합니다.

Q15. root 대신 Application User를 두는 이유는 무엇인가요?
A.

Application이 실제 필요한 범위보다 과도한 Database 권한을 갖지 않도록 하기 위해서입니다.

Q16. DB Password를 Source Code와 분리하는 이유는 무엇인가요?
A.

Password 같은 Secret을 Git이나 Application Logic에 직접 포함하지 않고 환경별 설정으로 관리하기 위해서입니다.

Q17. Parameterized Query와 최소 권한은 같은 보안 방식인가요?
A.

아닙니다. Parameterized Query는 SQL Code와 외부 Data를 분리하고, 최소 권한은 Account가 실행할 수 있는 Operation과 범위를 제한합니다.

Q18. SQLite와 PyMySQL의 Placeholder 차이는 무엇인가요?
A.

SQLite의 대표 위치 기반 Placeholder는 ?이고, 교안의 PyMySQL 예에서는 %s를 사용합니다.

Q19. Privilege와 Transaction은 어떻게 다른가요?
A.

Privilege는 SQL을 실행할 수 있는지 결정하고, Transaction은 실행한 변경을 확정하거나 취소하는 문제입니다.

Q20. Repository와 최소 권한은 어떻게 연결할 수 있나요?
A.

Repository가 실제 실행하는 SQL Operation을 분석하여 Application Account에 필요한 Privilege만 부여하는 방향으로 연결할 수 있습니다.

Memory

오늘의 암기 포인트

  • MySQL Account는 User + Host로 이해한다.
  • 대표 표현은 'app_user'@'localhost'이다.
  • root와 Application User의 역할을 구분한다.
  • CREATE USER는 Account 생성이다.
  • GRANT는 Privilege 부여다.
  • Account 생성과 Database 작업 권한은 같은 것이 아니다.
  • 로그인 성공과 모든 SQL 실행 가능은 같은 것이 아니다.
  • SELECT, INSERT, UPDATE, DELETE를 주요 Application Privilege로 기억한다.
  • *.*는 넓고, db.*, db.table로 범위를 줄일 수 있다.
  • 최소 권한은 필요한 권한만 + 필요한 범위에만이다.
  • Step 1·2 보완에서는 SHOW GRANTS로 실제 권한을 확인한다.
  • REVOKE는 권한 제거, DROP USER는 Account 제거다.
  • ALTER USER는 기존 Account 변경이다.
  • Host가 다르면 같은 User 이름도 다른 접속 조건으로 봐야 한다.
  • Password는 Source Code와 분리한다.
  • Application 외부 값은 Parameter Binding으로 SQL에 전달한다.
  • Privilege와 Transaction은 서로 다른 책임이다.
