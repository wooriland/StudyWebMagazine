Scrapy Shell과 프로젝트 구조

지금까지는 requests, BeautifulSoup, Selenium을 이용해 개발자가 직접 요청·분석·Browser 제어 흐름을 만들었습니다. 이번 단원부터는 Request · Response · Spider · Item · Pipeline · Settings를 역할별로 분리하는 Scrapy Framework 로 넘어갑니다. 먼저 Scrapy Shell에서 Response와 CSS·XPath Selector를 대화식으로 검증하고, scrapy startproject로 생성되는 프로젝트의 각 파일이 어떤 책임을 갖는지 공부합니다.

핵심 공식 Shell에서 검증 → Selector 확정 → Project 생성 → 역할 분리 → Spider 구현
Target Page → Scrapy Shell → Response → CSS / XPath → startproject → Project

학습 목표

  • Scrapy가 단순 HTTP Library가 아니라 Crawling Framework인 이유를 설명할 수 있다.
  • Requests 방식과 Scrapy Framework 방식의 실행 구조 차이를 설명할 수 있다.
  • Scrapy Shell을 Spider 작성 전 Response·Selector 검증 도구로 사용할 수 있다.
  • response.status, response.url, response.text를 이용해 응답 상태를 확인할 수 있다.
  • view(response)의 목적을 이해한다.
  • response.css()와 response.xpath()의 차이를 설명할 수 있다.
  • CSS의 ::text, ::attr()를 사용할 수 있다.
  • XPath의 text(), @attribute, ./의 의미를 설명할 수 있다.
  • Selector와 SelectorList를 구분할 수 있다.
  • get()과 getall()의 반환 결과를 구분할 수 있다.
  • 교안의 extract_first(), extract()을 현재 학습의 get(), getall()과 연결할 수 있다.
  • None, 빈 리스트, IndexError를 서로 구분할 수 있다.
  • Scrapy에서도 Card-first 방식으로 레코드 관계를 유지할 수 있다.
  • scrapy startproject로 프로젝트 구조를 생성할 수 있다.
  • spiders/, items.py, pipelines.py, settings.py, middlewares.py, scrapy.cfg의 역할을 구분할 수 있다.
  • Pipeline Priority가 낮을수록 먼저 실행된다는 구조를 이해한다.
  • HTTP 문제와 Selector 문제를 서로 다른 계층으로 디버깅할 수 있다.
  • Browser DOM과 Scrapy Response가 다를 수 있다는 점을 설명할 수 있다.
  • 다음 단원에서 Shell의 Selector가 Spider의 parse(response)로 이동하는 이유를 이해한다.
01

Core Concept

Scrapy Framework의 핵심 구조

이번 단원에서 가장 먼저 바꿔야 할 생각은 “Scrapy는 requests보다 편한 get() 함수”가 아니라 “Crawling의 여러 책임을 나누어 관리하는 Framework” 라는 점입니다.

Library와 Framework의 관점 차이

LIBRARY

requests 중심

내 코드 → requests.get()

개발자가 실행 흐름을 직접 만들고 필요한 Library 함수를 호출합니다.

FRAMEWORK

Scrapy 중심

Scrapy → Spider 규칙

Framework가 전체 흐름을 관리하고 개발자는 정해진 역할에 Crawling 규칙을 작성합니다.

requests는 “내가 흐름을 만든다”. Scrapy는 “Framework 흐름 안에 내 규칙을 넣는다”.

규모가 커질수록 Scrapy가 필요한 이유

URL 수백·수천 Page 다음 Request 관리
LINK 상세 페이지 추적 새 Request 생성
DATA Field 구조 증가 Item Schema
CLEAN 정제·검증 Pipeline
STORE 파일·DB 저장 Repository 역할
CONFIG 전역 운영 설정 settings.py

Scrapy 전체 데이터 흐름

→

→
3 Downloader Page 다운로드
→

→
5 Spider 분석·추출

CRAWL New Request → Scheduler

05

Common Mistakes

Scrapy 입문에서 자주 하는 실수

01

Scrapy를 requests의 고급 get() 함수라고 생각

Scrapy는 Request·Response·Spider·Item·Pipeline 등 여러 책임이 연결되는 Framework입니다.

02

Shell 검증 없이 바로 Spider부터 작성

Selector 문제와 Spider 구조 문제를 동시에 디버깅하게 될 수 있습니다.

03

response.css()가 문자열을 반환한다고 생각

먼저 SelectorList/Selector가 만들어지고 실제 문자열 추출은 get(), getall() 단계에서 일어납니다.

04

get()과 getall()을 혼동

get() → 하나 getall() → 전체
05

빈 SelectorList에 바로 [0] 사용

Matching 결과가 없다면 Python의 IndexError로 이어질 수 있습니다.

06

CSS에서 ::text를 빼먹음

Tag HTML과 실제 Text를 구분해야 합니다.

07

Text와 Attribute를 같은 방식으로 찾음

::text ::attr(href)
08

CSS와 XPath 문법을 섞음

response.css()에는 CSS, response.xpath()에는 XPath 표현식을 사용합니다.

09

Browser에 보이면 Response에도 있다고 생각

JavaScript 실행 이후 Browser DOM과 Scrapy가 받은 Response HTML은 다를 수 있습니다.

10

403인데 Selector부터 수정

08

Interview Point

Scrapy Shell과 Project 면접 핵심 질문

Q1 Scrapy란 무엇인가요?

A.

Request·Response·Spider·Item·Pipeline·Settings 등의 역할을 나누어 반복 Crawling과 데이터 처리를 구조화하는 Python 기반 Crawling Framework입니다.

Q2 Requests와 Scrapy의 차이는?

A.

Requests는 HTTP Client Library이고, Scrapy는 Request Scheduling부터 Response 처리, 데이터 구조와 후처리까지 관리하는 Framework입니다.

Q3 Selenium과 Scrapy의 차이는?

A.

Selenium은 실제 Browser 상태와 사용자 행동을 자동화하고, Scrapy는 Request·Response 중심의 반복 Crawling을 구조화합니다.

Q4 Scrapy Shell은 무엇인가요?

A.

Spider를 완성하기 전에 Response와 CSS/XPath Selector를 대화식으로 시험하는 환경입니다.

Q5 Shell에서 무엇부터 확인해야 하나요?

A.

response.status → response.url → response.text → Selector 순서로 확인합니다.

Q6 response란 무엇인가요?

A.

Scrapy가 요청 결과로 받은 Response 객체입니다. URL, HTTP 상태와 응답 본문을 확인하고 CSS·XPath Selector를 사용할 수 있습니다.

Q7 response.css()는 바로 문자열인가요?

A.

아닙니다. SelectorList 흐름으로 이해하고 실제 문자열은 get() 또는 getall()로 추출합니다.

Q8 get()과 getall() 차이는?

A.

get()은 첫 결과, getall()은 모든 결과를 리스트로 가져옵니다.

Q9 결과가 없으면 어떻게 되나요?

A.

이번 학습 기준으로 get()은 None, getall()은 빈 리스트로 해석합니다.

Q10 extract()와 extract_first()은?

A.

교안에서 사용하는 추출 방식이며, 각각 전체 결과와 첫 결과를 의미합니다. Step 1·2에서는 각각 getall(), get()과 연결해 학습했습니다.

Q11 Scrapy는 CSS와 XPath를 모두 쓰나요?

A.

네. response.css()와 response.xpath()를 사용할 수 있습니다.

Q12 CSS에서 Text와 Attribute는?

A.

Text는 ::text, Attribute는 ::attr(href) 형태를 사용합니다.

Q13 XPath에서 Text와 Attribute는?

A.

Text는 text(), Attribute는 @href와 같이 표현합니다.

Q14 spiders/의 역할은?

A.

어떤 사이트를 Crawling하고 무엇을 Scraping할지, 다음 어떤 Request를 만들지 정의하는 Spider Class 위치입니다.

Q15 items.py의 역할은?

A.

수집 결과가 어떤 Field 구조를 가질지 정의하는 역할입니다.

Q16 pipelines.py의 역할은?

A.

Spider가 생성한 Item을 받아 Cleaning·Validation·Duplicate 처리·저장 등을 담당합니다.

Q17 settings.py의 역할은?

A.

Spider와 Pipeline을 포함한 Scrapy Project의 세부 동작 설정을 관리합니다.

Q18 Pipeline 숫자의 의미는?

A.

Pipeline 실행 순서를 결정합니다. 낮은 값의 Pipeline이 먼저 실행됩니다.

Q19 왜 Shell에서 먼저 Selector를 시험하나요?

A.

HTTP·Response·Selector 문제를 Spider 코드와 분리해 확인하여 디버깅 범위를 줄일 수 있기 때문입니다.

Q20 Browser에는 데이터가 있는데 Scrapy에 없으면?

A.

JavaScript 이후 Browser DOM과 Scrapy Response가 다른지 확인하고, Network의 Fetch/XHR 등 실제 데이터 요청을 살펴봅니다.

None vs []

Item vs Pipeline

Outer Folder vs Inner Package

Project Root와 Python Package를 구분합니다.

Selenium vs Scrapy

Browser 상태 자동화와 반복 Crawling Framework라는 역할 차이입니다.
