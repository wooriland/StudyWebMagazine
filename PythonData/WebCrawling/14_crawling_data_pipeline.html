Scheduling — 언제 다시 실행할 것인가?

WHEN Schedule Rule every().day.at(...)
WHAT Job run_pipeline() 
schedule.every(
    10
).seconds.do(
    job
)


while True:

    schedule.run_pending()

    time.sleep(
        1
    )
Rule 등록 → run_pending() → job() → run_pipeline()
Scheduler는 Crawling Logic이 아니다.

Scheduler는 “언제 실행할지”를 결정하고, run_pipeline()이 실제 수집·정제·저장을 담당합니다.

from datetime import datetime


def add_metadata(

):

    collected_at = (

            timespec="seconds"

    for record in records:

    return records

예제 12. SQLite 저장 — 보완 학습 

import sqlite3


def save_db(
    records,
    path,
):

    with sqlite3.connect(
        path
    ) as conn:

        conn.execute(
            """
            CREATE TABLE IF NOT EXISTS crawl_news (

                id INTEGER
                    PRIMARY KEY AUTOINCREMENT,

                news_id TEXT,

                title TEXT,

                category TEXT,

                link TEXT,

                source_url TEXT,

                collected_at TEXT NOT NULL

            )
            """
        )


        sql = """
            INSERT INTO crawl_news (
                news_id,
                title,
                category,
                link,
                source_url,
                collected_at
            )
            VALUES (?, ?, ?, ?, ?, ?)
        """


        rows = [
            (
                record["news_id"],
                record["title"],
                record.get("category"),
                record.get("link"),
                record.get("source_url"),
                record["collected_at"],
            )
            for record in records
        ]


        conn.executemany(
            sql,
            rows,
        )

예제 13. requests + BeautifulSoup Collector 

import requests

from bs4 import BeautifulSoup


def collect_news(
    url,
):

    response = requests.get(
        url,
        timeout=10,
    )


    response.raise_for_status()


    soup = BeautifulSoup(
        response.text,
        "html.parser",
    )


    cards = soup.select(
        "article.news-item"
    )


    records = []


    for card in cards:

        title_tag = card.select_one(
            ".title"
        )


        category_tag = card.select_one(
            ".category"
        )


        link_tag = card.select_one(
            "a.detail"
        )


        record = {
            "news_id":
                card.get(
                    "data-id"
                ),

            "title":
                (
                    title_tag.get_text()
                    if title_tag
                    else None
                ),

            "category":
                (
                    category_tag.get_text()
                    if category_tag
                    else None
                ),

            "link":
                (
                    link_tag.get(
                        "href"
                    )
                    if link_tag
                    else None
                ),

            "source_url":
                url,
        }


        records.append(
            record
        )


    return records

def run_pipeline():

    records = collect_news(
        TARGET_URL

Common Mistakes

최종 프로젝트에서 자주 하는 실수

01

Crawling 성공만 확인하고 저장하지 않는다

print(records)만 하고 종료하면 Memory의 값은 사라집니다.

02

Raw Data를 바로 저장한다

공백·형식·결측치를 정리한 뒤 저장하는 흐름을 분리합니다.

03

Validation 없이 모든 Record를 저장한다

어떤 Field가 필수인지 먼저 결정합니다.

04

ensure_ascii와 UTF-8을 같은 것으로 생각한다

ensure_ascii → JSON 표현 encoding → File 문자
05

json.dumps()가 File까지 저장한다고 생각한다

dumps() → str dump() → file
06

json.loads()의 방향을 반대로 기억한다

loads()는 JSON String을 Python Object로 변환합니다.

07

403 Error Page를 JSON으로 Parsing한다

JSONDecodeError 전에 HTTP Status와 Body를 확인합니다.

08

JSON 전체 Document를 무작정 Append한다

Snapshot인지 History인지 먼저 결정하고, 누적이 필요하면 JSONL·DB도 검토합니다.

09

CSV를 split(",")만으로 처리한다

Field 내부 Comma와 Quote 규칙 때문에 표준 csv Module이 필요합니다.

10

CSV File의 newline=""을 빠뜨린다

교안에서도 CSV 쓰기 시 빈 줄 문제와 연결해서 설명하는 부분입니다.

11

Record마다 Field 구조가 다르다

저장 전에 공통 Schema를 먼저 고정합니다.

12

DictWriter fieldnames와 Record Key가 다르다

Expected Schema와 Actual Record를 비교합니다.

13

Snapshot과 History를 구분하지 않는다

덮어쓸 데이터인지 시간별로 누적할 데이터인지 저장 전에 결정합니다.

14

SQL 문자열에 Crawling 값을 직접 붙인다

Parameter Placeholder로 SQL과 Data를 분리합니다.

15

Pipeline 검증 전에 Scheduler부터 연결한다

먼저 python app.py로 한 번의 실행을 완전히 검증합니다.

16

Schedule Rule만 등록하면 실행된다고 생각한다

run_pending()을 호출하는 실행 Loop가 필요합니다.

17

Program이 꺼져 있어도 schedule이 실행된다고 생각한다

학습 예제의 Scheduler Process가 종료되면 Job도 실행되지 않습니다.

18

Job Exception을 처리하지 않는다

Network Error 한 번이 전체 반복 실행에 영향을 주지 않도록 Job 단위 Logging을 고려합니다.

19

Schedule 주기보다 Crawling 시간이 더 길다

Job 수행 시간까지 포함해 적절한 반복 주기를 설계해야 합니다.

20

Scheduler 실행마다 DB에 중복을 무조건 Insert한다

현재 상태를 유지할 것인지, History를 저장할 것인지 먼저 결정합니다.

21

source_url과 collected_at을 남기지 않는다

원본과 수집 시점을 추적하기 어려워집니다.

22

JSON·CSV·DB를 모든 프로젝트에 전부 사용한다

이번 학습에서는 비교를 위해 모두 사용하지만 실제 프로젝트에서는 목적에 맞게 선택합니다.

Interview Point

최종 Web Crawling 면접 질문

Q1 Crawling Data Pipeline이란 무엇인가요?

A.

웹에서 데이터를 수집하는 것뿐 아니라 Parsing, Normalize, Validation, Storage와 반복 실행까지 연결한 전체 데이터 처리 흐름입니다.

Q2 왜 list[dict] 형태가 유용한가요?

A.

수집 도구와 저장 방식을 분리할 수 있고, JSON·CSV·DB·Pandas 등의 공통 중간 데이터 구조로 사용하기 쉽기 때문입니다.

Q3 JSON은 무엇인가요?

A.

JavaScript Object Notation의 약자로 구조화된 데이터를 Text 형태로 표현하는 경량 Data Format입니다.

Q4 dumps()와 loads()의 차이는 무엇인가요?

A.

dumps()는 Python Object를 JSON String으로, loads()는 JSON String을 Python Object로 변환합니다.

Q5 dump()와 dumps()의 차이는?

A.

dumps()는 JSON 문자열을 만들고, dump()는 JSON을 File에 쓰는 흐름에 사용합니다.

Q6 ensure_ascii=False를 사용하는 이유는?

A.

한글 같은 비 ASCII 문자를 Escape Sequence가 아니라 문자 그대로 표현하기 위해 사용할 수 있습니다.

Q7 ensure_ascii와 UTF-8은 같은 것인가요?

A.

아닙니다. ensure_ascii는 JSON 문자 표현이고, UTF-8은 File Character Encoding입니다.

Q8 JSONDecodeError가 나면 무엇을 확인하나요?

A.

먼저 HTTP Status와 실제 Response Body가 JSON인지 확인한 뒤 JSON 문법을 확인합니다.

Q9 CSV는 무엇인가요?

A.

Comma-Separated Values의 약자로 데이터를 행·열 중심의 Text Format으로 저장하는 방식입니다.

Q10 CSV를 split(",")만으로 처리하지 않는 이유는?

A.

Field 안에도 Comma가 들어갈 수 있고 Quote·Escape 규칙이 있기 때문에 표준 csv Module을 사용하는 것이 좋습니다.

Q11 csv.DictWriter가 Crawling에 유용한 이유는?

A.

Crawling 결과를 Dictionary로 구조화한 경우 Key와 CSV Column을 직접 연결하기 쉽기 때문입니다.

Q12 newline=""은 왜 사용하나요?

A.

CSV Module이 Newline을 처리할 수 있도록 File Open 단계에서 설정하는 옵션입니다.

Q13 CSV 열 불일치를 어떻게 방지하나요?

A.

먼저 Field Schema를 고정하고, 모든 Record가 동일한 Key 구조를 갖는지 Validation한 뒤 저장합니다.

Q14 JSON과 CSV의 차이는?

A.

JSON은 구조적·중첩 데이터 표현에 유리하고, CSV는 일정한 행·열 구조와 Excel·Pandas 연결에 유리합니다.

Q15 Database는 언제 필요하나요?

A.

데이터가 지속적으로 누적되고 검색·중복 관리·History·관계 관리가 필요할수록 Database가 유리합니다.

Q16 Snapshot과 History의 차이는?

A.

Snapshot은 현재 상태를 대표하고, History는 여러 시점의 수집 상태를 누적합니다.

Q17 source_url은 왜 저장하나요?

A.

Record가 어느 Page에서 수집되었는지 다시 추적하고 검증하기 위해서입니다.

Q18 collected_at은 왜 필요한가요?

A.

반복 Crawling에서 해당 값이 어느 시점에 수집된 데이터인지 구분하기 위해 필요합니다.

Q19 Scheduling이 필요한 이유는?

A.

가격·뉴스·운영정보처럼 변하는 데이터를 사람이 매번 실행하지 않고 정해진 주기로 다시 수집하기 위해서입니다.

Q20 Schedule Rule과 job()의 차이는?

A.

Schedule Rule은 언제 실행할지, job은 무엇을 실행할지를 담당합니다.

Q21 run_pending()은 무엇을 하나요?

A.

등록된 Job 중 현재 실행 시점이 된 Job을 확인해 실행합니다.

Q22 Scheduler를 사용하면 Program을 꺼도 실행되나요?

A.

이번 교안의 Python schedule 방식에서는 Scheduler Process가 실행 중이어야 합니다.

Q23 requests와 Selenium은 언제 구분하나요?

A.

원하는 데이터가 HTTP Response에 이미 있다면 requests가 단순하고, Browser JavaScript 실행·Click·Login 같은 상태가 필요하면 Selenium을 검토합니다.

Q24 Scrapy는 언제 사용하나요?

A.

여러 URL, Pagination, Link Follow, Item·Pipeline 구조가 필요한 반복 Crawling에 적합합니다.

Q25 Web Crawling 최종 Pipeline을 설명해 주세요.

A.

Source에서 데이터를 Collect하고, 필요한 값을 Parse한 뒤 Normalize와 Validate를 거쳐 JSON·CSV·DB에 Store하고, 필요한 경우 Schedule로 반복 실행합니다.

  • CSV = 행·열
  • DB = 검색·누적·History
  • json.dumps() = Python → JSON String

  • encoding="utf-8" = File Encoding

  • JSONDecodeError = 실제 Input이 JSON인지 먼저 확인
  • CSV는 단순 split(",")보다 csv Module
  • csv.reader() = CSV Row 읽기
  • csv.writer() = List Row 쓰기
  • csv.DictWriter() = dict → CSV

  • CSV Schema = Record Key를 일정하게
  • CSV 열 불일치 = Schema부터 확인
  • Snapshot = 현재 상태
  • History = 시간별 누적

헷갈리기 쉬운 개념

Crawling vs Data Pipeline

데이터를 가져오는 동작과 가져온 데이터를 정제·검증·저장·반복하는 전체 흐름의 차이입니다.

dumps() vs dump()

JSON String 생성과 JSON File 쓰기를 구분합니다.

loads() vs load()

JSON String 읽기와 JSON File 읽기를 구분합니다.

ensure_ascii vs UTF-8

JSON 내부 문자 표현과 File Character Encoding의 차이입니다.

JSON vs JSONL

하나의 JSON Document와 한 줄에 Record 하나를 저장하는 형식의 차이입니다.

csv.reader vs DictReader

Row를 List로 읽는 방식과 Header 기반 Dictionary로 읽는 방식을 구분합니다.

writer vs DictWriter

List Row와 Dictionary Row를 저장하는 방식의 차이입니다.

Raw vs Normalized

추출 직후의 값과 일정한 규칙으로 정리된 값의 차이입니다.

Normalize vs Validate

값을 정리하는 과정과 사용 가능한 데이터인지 판단하는 과정의 차이입니다.

Snapshot vs History

현재 상태만 보존하는 방식과 시간별 상태를 누적하는 방식입니다.

Schedule Rule vs Job

언제 실행할지와 무엇을 실행할지를 구분합니다.

HTTP Timeout vs Selenium Timeout

HTTP Response와 Browser Condition 대기의 차이입니다.

Static vs Dynamic

Response에 이미 데이터가 있는 페이지와 Browser JavaScript 상태가 필요한 페이지를 구분합니다.

File vs Database

간단한 결과 보관과 검색·누적·관계 관리 목적을 구분합니다.
