Git/GitHub - Chapter 15

Fork / PR / Collaborator 팀 작업

다른 사람의 GitHub Repository에 직접 Push할 권한이 없다면, 원본을 Fork하여 내 GitHub 계정에서 작업하고 Pull Request로 변경을 제안할 수 있습니다.
같은 프로젝트 팀이라면 저장소 소유자가 팀원을 Collaborator로 초대하고, 같은 Repository 안에서 기능 Branch를 공유할 수 있습니다.
두 방식 모두 최종적으로 Feature Branch → Push → Pull Request → Review → Checks → Merge 흐름으로 연결됩니다.
이번 단원의 중심 질문은 “다른 사람의 저장소에는 어떻게 안전하게 기여하고, 같은 팀 저장소에서는 어떤 권한과 절차로 코드를 공유해야 할까?” 입니다.

01

이번 단원의 전체 지도

GitHub 팀 작업은 먼저 원본 Repository에 직접 Push할 권한이 있는가를 기준으로 나누면 이해하기 쉽습니다.

권한 없음

Fork 기반 협업

원본 Repository ↓ Fork 내 GitHub Fork ↓ Clone 내 Local Repository ↓ Branch 작업·Push 내 Fork Feature Branch ↓ Pull Request 원본 main

오픈소스나 외부 기여처럼 원본에 직접 Push할 수 없을 때 사용합니다.

권한 있음

Collaborator 기반 협업

팀 Repository ↓ Collaborator 초대 팀원 초대 수락 ↓ Clone Feature Branch 작업 ↓ 팀 Repository Push Pull Request ↓ Review·Merge 팀 main

사내 프로젝트, 학습 팀 프로젝트처럼 구성원이 정해진 경우 사용합니다.

두 방식의 공통 목적

독립 Branch → Push → Pull Request → Code Review → Checks → Merge

03

왜 Fork가 필요한가?

모두 원본 main에 직접 Push

원본 프로젝트가 위험해짐

  • 검토되지 않은 코드가 즉시 반영될 수 있습니다.
  • 악성 코드나 실수로 프로젝트가 손상될 수 있습니다.
  • 수많은 외부 사용자의 권한을 관리하기 어렵습니다.
  • 변경 목적과 검토 과정을 기록하기 어렵습니다.
  • main의 안정성과 배포 가능성을 보장하기 어렵습니다.
Fork에서 작업 후 PR

원본을 보호하며 변경 제안

  • 원본 Repository는 직접 수정되지 않습니다.
  • Contributor는 자신의 Fork에서 자유롭게 작업합니다.
  • 변경 내용은 PR의 Diff로 검토할 수 있습니다.
  • Maintainer가 Merge 또는 Close를 결정합니다.
  • Review와 CI를 통과한 변경만 반영할 수 있습니다.
Fork의 핵심 역할

권한이 없는 사람도 원본을 훼손하지 않고 안전하게 변경을 제안할 수 있게 합니다.

        ↓

MERGE COMMIT

Branch 통합 지점을 남김

          D ── E
         /      \

         \      /
          F ────

  • Merge Commit으로 통합 지점을 기록합니다.
  • Branch 구조가 History에 명확히 보입니다.

  • main History를 단순하게 유지할 수 있습니다.
  • Feature Branch의 세부 Commit은 하나로 합쳐집니다.
REBASE AND MERGE

Base 위에 Commit을 다시 적용

A ── B ── C ── D' ── E'
  • Merge Commit 없이 직선 History를 만듭니다.
  • Commit이 새 위치에 다시 생성되어 ID가 달라질 수 있습니다.

팀의 Merge 전략을 먼저 확인합니다

세 방식 중 하나가 항상 정답인 것은 아닙니다. Repository의 History 정책과 팀 규칙에 따라 선택합니다.

CONFLICT CAUSE

원본 main과 Feature Branch가 갈라짐

          내 Feature Commit
         /
A ── B
         \
          upstream main 새 Commit

같은 파일의 같은 부분을 수정했다면 PR이 자동 Merge되지 않을 수 있습니다.

RESOLUTION

최신 Base를 Feature Branch에 반영

git switch feature/login
git merge upstream/main

# Conflict 해결
git add .
git commit
git push

같은 Branch에 Push하면 기존 PR이 자동으로 갱신됩니다.

PR Merge 후 Fork main 동기화

PR Merge 후 정리

초보자가 자주 하는 실수

1. 원본 Repository를 Clone하고 Push

Fork 기여자는 원본이 아닌 자신의 Fork를 Clone해야 합니다.

2. Fork와 Clone을 같은 기능으로 이해

Fork는 GitHub 간 복사이고 Clone은 GitHub에서 PC로 가져오는 작업입니다.

3. Fork와 Branch를 혼동

Fork는 Repository 단위이고 Branch는 Repository 내부 작업선입니다.

4. Fork main에서 여러 작업 진행

서로 다른 작업이 하나의 PR에 섞일 수 있습니다.

5. origin을 원본으로 착각

내 Fork를 Clone했다면 origin은 내 Fork입니다.

6. upstream을 등록하지 않음

원본 최신 변경을 가져오는 기준 Remote가 없어집니다.

7. 오래된 Fork에서 작업 시작

최신 upstream 변경이 없어 Conflict 범위가 커질 수 있습니다.

8. Base와 Compare를 반대로 선택

변경 방향과 포함 Commit이 예상과 달라질 수 있습니다.

9. git pull과 PR을 같은 것으로 이해

하나는 Git 명령이고 다른 하나는 GitHub 협업 기능입니다.

10. Feature Branch를 Push하지 않고 PR 생성

GitHub에 Compare Branch가 존재해야 PR을 만들 수 있습니다.

11. PR 생성 즉시 자동 Merge된다고 생각

Review, CI, Conflict와 권한 조건을 통과해야 합니다.

12. 수정 요청마다 새 PR 생성

기존 Feature Branch에 추가 Commit을 Push하면 PR이 갱신됩니다.

13. 하나의 PR에 여러 목적 포함

작고 명확한 단위로 Branch와 PR을 분리합니다.

14. Collaborator가 main에 직접 Push

권한이 있어도 팀 규칙과 Branch Protection을 따라야 합니다.

15. 공통 GitHub 계정과 PAT 공유

개인 계정과 개인 Credential을 사용해야 합니다.

16. PR Merge 후 Fork 동기화 생략

다음 작업을 오래된 main에서 시작할 수 있습니다.

면접 포인트

Q1. Fork란 무엇인가요?

다른 사람의 GitHub Repository를 내 계정 아래에 연결된 별도 Repository로 만드는 기능입니다. 원본에 직접 Push 권한이 없어도 자신의 Fork에서 작업하고 PR을 보낼 수 있습니다.

Q2. Fork와 Clone의 차이는 무엇인가요?

Fork는 GitHub Repository를 내 GitHub 계정 아래에 만드는 작업이고, Clone은 Remote Repository를 내 PC의 Local Repository로 복제하는 작업입니다.

Q3. Fork와 Branch의 차이는 무엇인가요?

Fork는 Repository 단위의 분리이고, Branch는 하나의 Repository 안에서 작업 History를 나누는 기능입니다.

Q4. Fork 방식에서 origin과 upstream은 무엇인가요?

origin은 내 Fork이며 내가 주로 Push하는 곳입니다. upstream은 원본 Repository이며 원본의 최신 변경을 가져오는 곳입니다.

Q5. Pull Request란 무엇인가요?

한 Branch의 변경을 다른 Base Branch에 Merge하도록 제안하고, 변경 내용을 토론·검토·승인하는 GitHub 협업 기능입니다.

Q6. git pull과 Pull Request의 차이는 무엇인가요?

git pull은 Remote 변경을 Local Branch로 가져오는 명령이고, Pull Request는 Branch 변경의 검토와 Merge를 요청하는 GitHub 기능입니다.

Q7. Base Branch와 Compare Branch는 무엇인가요?

Base Branch는 변경을 받을 대상이고, Compare 또는 Head Branch는 변경 내용을 제공하는 작업 Branch입니다.

Q8. PR 생성 후 추가 수정은 어떻게 반영하나요?

같은 Head Branch에서 수정·Commit한 뒤 동일한 Remote Branch로 Push하면 기존 PR이 자동으로 갱신됩니다.

Q9. Draft Pull Request란 무엇인가요?

아직 Merge나 정식 Review 준비가 끝나지 않은 작업을 미리 공유하는 PR입니다. 완성 후 Ready for review로 전환합니다.

Q10. Review 결과에는 무엇이 있나요?

일반 의견을 남기는 Comment, 변경을 승인하는 Approve, Merge 전 수정을 요구하는 Request Changes가 있습니다.

Q11. Collaborator란 무엇인가요?

Repository 소유자로부터 같은 Repository에서 협업할 권한을 부여받은 사용자입니다.

Q12. Fork와 Collaborator 방식은 언제 사용하나요?

Fork는 원본에 직접 Push 권한이 없는 오픈소스나 외부 기여에 사용하고, Collaborator는 구성원이 정해진 내부 팀 프로젝트에 사용합니다.

Q13. Branch Protection이란 무엇인가요?

중요 Branch의 직접 Push나 Force Push를 제한하고, PR Review와 Status Check를 Merge 조건으로 적용하는 규칙입니다.

Q14. Pull Request가 Merge되지 않는 이유는 무엇인가요?

Conflict, 필수 Review 부족, CI Check 실패, Draft 상태, Branch Protection 또는 Merge 권한 부족 등이 있습니다.

Q15. Fork를 원본과 동기화하는 순서는 무엇인가요?

upstream을 Fetch하고 Local main에 Merge한 뒤, 갱신된 Local main을 origin main으로 Push합니다.

학습 메모

오늘의 암기 포인트

  • Fork는 GitHub에서 GitHub로 Repository를 만듭니다.
  • Clone은 GitHub Repository를 내 PC로 가져옵니다.
  • Fork 방식의 origin은 내 Fork이고 upstream은 원본입니다.
  • Pull Request는 Branch 변경의 검토와 Merge를 요청합니다.
  • Collaborator는 같은 Repository의 협업 권한을 부여받은 사용자입니다.
  • 권한이 있어도 main 직접 Push보다 Feature Branch와 PR이 안전합니다.

협업 방식 빠른 비교

Fork 원본 권한 없는 외부 기여
Collaborator 권한을 부여받은 내부 팀원
origin 내 Fork 또는 팀 Repository
upstream Fork의 원본 Repository

PR 방향 암기

Base

변경을 받을 Branch

main
Compare / Head

변경을 제공하는 Branch

feature/login

Fork 핵심 명령

Remote 확인 git remote -v
upstream 추가 git remote add upstream URL
원본 Fetch git fetch upstream
원본 main 반영 git merge upstream/main
Feature Branch git switch -c feature/login
Feature Push git push -u origin feature/login
Local Branch 삭제 git branch -d feature/login
Remote Branch 삭제 git push origin --delete feature/login

Review 결과

Comment 일반 의견과 질문
Approve 현재 변경 승인
Request Changes Merge 전 수정 요구

오류 메시지 빠른 분류

  • 403: Push 대상과 계정·PAT·권한 확인
  • Repository not found: URL과 접근 권한 확인
  • upstream already exists: 기존 Remote URL 확인
  • no upstream branch: git push -u로 연결
  • non-fast-forward: Remote 변경을 먼저 통합
  • nothing to compare: Base·Compare와 Commit 확인
  • branch has conflicts: 최신 Base 반영 후 Conflict 해결
  • required check failed: CI 실패 로그 확인
  • review required: 필요한 Approve 획득
  • protected branch: 직접 Push 대신 PR 사용
