Git/GitHub - Chapter 12

Pull / Fetch / Merge로 버전 맞추기

Local Repository에서 새로운 Commit을 만들었는데 GitHub Remote Repository에도 내가 가지고 있지 않은 Commit이 존재하면,
Git은 원격 History를 보호하기 위해 Push를 거절할 수 있습니다.

이번 단원에서는 Push rejected가 왜 발생하는지, Pull과 Fetch는 무엇이 다른지, origin/main을 Local main에 어떻게 Merge하는지,
그리고 Conflict를 해결한 뒤 Push HEAD를 실행하는 과정을 학습합니다.

이번 단원의 중심 질문은 “내 Commit과 원격 Commit이 서로 갈라졌을 때 두 History를 어떻게 안전하게 하나로 합칠 수 있을까?” 입니다.

02

main · origin/main · HEAD 구분하기

Pull과 Fetch를 이해하려면 세 포인터가 어디를 가리키는지 먼저 구분해야 합니다.

HEAD

현재 작업 위치

현재 Checkout된 Branch 또는 Commit을 가리키는 포인터입니다. 일반적으로 HEAD → main 관계가 됩니다.

main

Local Branch

내 컴퓨터에서 직접 수정하고 Commit하는 Branch입니다. Local Commit이 생성되면 main이 새 Commit으로 이동합니다.

origin/main

Remote Tracking Branch

마지막 Fetch 또는 Pull 시점에 확인한 GitHub main의 상태를 Local에서 나타냅니다.

GitHub main

실제 Remote Branch

GitHub 서버에 존재하는 실제 Branch입니다. Fetch해야 최신 상태가 origin/main에 반영됩니다.

Commit A
→
Commit B
→

HEAD main origin/main

origin/main은 GitHub 서버 자체가 아닙니다

GitHub에서 새 Commit이 만들어져도 Fetch하기 전까지 내 컴퓨터의 origin/main은 이전 Commit을 가리킬 수 있습니다.

03

Local과 Remote의 네 가지 상태

명령어를 실행하기 전에 현재 상태가 동일, ahead, behind, diverged 중 무엇인지 먼저 판단해야 합니다.

UP TO DATE

Local과 Remote가 동일함

A ── B ── C
          ↑
 main, origin/main

추가로 가져오거나 보낼 Commit이 없습니다.

필요 작업: 없음
AHEAD

Local만 앞섬

A ── B ── C
     ↑       ↑
origin/main main

Local에만 새로운 Commit이 있습니다.

필요 작업: Push
BEHIND

Remote만 앞섬

A ── B ── C
     ↑       ↑
   main   origin/main

Remote에만 새로운 Commit이 있습니다.

필요 작업: Pull 또는 Merge
DIVERGED

Local과 Remote가 갈라짐

          L ← main
         /
A ── B
         \
          R ← origin/main

양쪽에 서로 없는 Commit이 존재합니다.

필요 작업: Merge 후 Push

현재 상태 확인

git status
git branch -vv
git log --oneline --decorate --graph --all
04

Fast-forward와 Merge Commit

FAST-FORWARD

Branch 포인터만 앞으로 이동

변경 전

A ── B ── C
     ↑       ↑
   main   origin/main


변경 후

A ── B ── C
          ↑
 main, origin/main

Local에 별도 Commit이 없으므로 새로운 Merge Commit 없이 main만 앞으로 이동합니다.

MERGE COMMIT

갈라진 History를 새 Commit으로 통합

          L
         / \
A ── B      M
         \ /
          R

Local과 Remote 양쪽에 새 Commit이 있어 두 부모를 가진 Merge Commit M이 만들어집니다.

Fast-forward 판단 기준

현재 Local Branch가 병합 대상 Branch의 과거 Commit을 가리키고 있다면 포인터만 앞으로 이동할 수 있습니다. History가 양쪽으로 갈라졌다면 Merge 과정이 필요합니다.

05

Push rejected는 왜 발생하는가?

Local과 Remote가 각각 다른 Commit을 만들었다고 가정합니다.

LOCAL

내 Eclipse에서 만든 Commit

          L ← main
         /
A ── B

Local Repository에는 L Commit이 존재합니다.

Push × rejected
REMOTE

GitHub에 먼저 올라간 Commit

A ── B
         \
          R ← remote main

GitHub에는 Local이 모르는 R Commit이 존재합니다.

대표 오류 메시지 
! [rejected] main -> main (non-fast-forward)
error: failed to push some refs

hint: Updates were rejected because the remote contains
work that you do not have locally.

Commit과 Push 결과를 분리해서 봅니다

Commit and Push에서 Push만 실패했다면 Local Commit은 사라진 것이 아닙니다. git log --oneline으로 확인할 수 있습니다.

07

Merge: origin/main을 현재 main에 통합하기

Fetch가 끝난 뒤 현재 Local Branch가 main이라면 다음 명령으로 원격 변경을 통합합니다.

MERGE SOURCE

origin/main

Fetch로 갱신한 Remote Tracking Branch입니다.

Merge → git merge origin/main
CURRENT BRANCH

main

현재 HEAD가 연결된 Local Branch입니다.

Merge 방향을 반대로 이해하지 않습니다

현재 main을 Checkout한 상태에서 origin/main을 선택해 Merge합니다. 즉, 원격 변경을 현재 Local main에 합치는 작업입니다.

Already up to date

합칠 새로운 Commit이 없습니다.

Fast-forward

Branch 포인터만 앞으로 이동했습니다.

Merged

자동 Merge 또는 Merge Commit이 생성되었습니다.

Conflicting

사용자가 직접 해결해야 할 충돌이 있습니다.

Failed

Working Tree 상태 등으로 Merge가 실패했습니다.

Push HEAD가 필요한 경우

Local 전용 Commit과 Remote 전용 Commit을 통합해 새로운 Merge 결과가 Local에 만들어졌을 때입니다.

Push HEAD가 필요 없는 경우

Remote만 앞선 상태에서 Pull이 단순 Fast-forward로 끝나 Local이 Remote Commit을 따라간 경우입니다.

Push HEAD가 하지 않는 일

새로운 Commit을 생성하거나 Conflict를 해결하지 않습니다. 이미 존재하는 Local History를 전송합니다.

Local 수정이 원격 변경으로 덮어써질 가능성이 있으므로 Git이 Pull 또는 Merge를 중단한 상태입니다.

방법 1

작업 완료 후 Commit

방법 2

수정 취소

방법 3

임시 보관

미완성 작업이라면 Stash가 필요할 수 있습니다.

초보자 기본 원칙

Pull 전에 git status를 확인하고, 가능한 경우 현재 작업을 의미 있는 Commit으로 정리합니다.

초보자가 자주 하는 실수

1. rejected를 인증 오류로 생각

non-fast-forward는 History 문제이고 403은 권한 문제입니다.

2. rejected 후 Force Push

원격의 다른 Commit을 삭제할 위험이 있습니다.

3. Fetch 후 파일이 안 바뀌어 실패로 판단

Fetch는 origin/main만 갱신하고 Working Tree는 바로 바꾸지 않습니다.

4. Pull과 Fetch를 같은 작업으로 이해

Pull은 가져온 뒤 통합하고 Fetch는 우선 가져오기만 합니다.

5. Merge 방향을 반대로 이해

현재 main에 origin/main을 합치는 흐름입니다.

6. origin/main을 GitHub 실시간 상태로 착각

origin/main은 마지막 Fetch 결과입니다.

7. Conflict에서 무조건 한쪽만 선택

두 변경을 조합한 새로운 최종 결과를 만들 수도 있습니다.

8. Conflict Marker를 남겨둠

최종 코드에서 모든 충돌 표시를 제거해야 합니다.

9. 충돌 수정 후 Add하지 않음

Add는 Git에게 Conflict 해결 완료를 알리는 단계입니다.

10. Pull 전에 미완성 변경을 방치

먼저 현재 작업을 Commit하거나 안전하게 보관해야 합니다.

11. Pull이 끝나면 항상 Push

단순 Fast-forward라면 원격에 새로 보낼 내용이 없습니다.

12. Push HEAD를 Commit 버튼으로 착각

Push HEAD는 이미 존재하는 Commit History를 전송합니다.

면접 포인트

Q1. Push가 non-fast-forward로 거절되는 이유는 무엇인가요?

원격 Branch에 Local Branch가 가지고 있지 않은 Commit이 있기 때문입니다. 그대로 Push하면 원격 History가 손실될 수 있으므로 Git이 Push를 거절합니다.

Q2. Fetch란 무엇인가요?

원격 저장소의 새로운 Commit과 Branch 정보를 Local Repository로 가져오고 origin/main 같은 Remote Tracking Branch를 갱신하는 작업입니다. 현재 Local Branch와 Working Directory는 바로 변경하지 않습니다.

Q3. Pull과 Fetch의 차이는 무엇인가요?

Fetch는 원격 정보를 가져오기만 합니다. Pull은 원격 정보를 가져온 뒤 현재 Local Branch에 통합합니다.

Q4. Merge란 무엇인가요?

다른 Branch의 Commit History를 현재 Checkout된 Branch에 통합하는 작업입니다. 상황에 따라 Fast-forward 또는 Merge Commit이 만들어질 수 있습니다.

Q5. Fast-forward란 무엇인가요?

현재 Branch가 병합 대상 Branch의 과거 Commit을 가리키고 있어 새로운 Merge Commit 없이 Branch 포인터만 앞으로 이동할 수 있는 상태입니다.

Q6. main과 origin/main의 차이는 무엇인가요?

main은 Local에서 직접 작업하는 Branch입니다. origin/main은 마지막 Fetch 시점의 원격 main 상태를 Local Repository 안에서 나타내는 Remote Tracking Branch입니다.

Q7. Conflict는 언제 발생하나요?

주로 같은 파일의 같은 영역을 서로 다른 Branch에서 다르게 수정한 뒤 Merge하거나 Pull할 때 Git이 최종 결과를 자동으로 판단하지 못하면 발생합니다.

Q8. Conflict 해결 순서는 무엇인가요?

충돌 파일을 수정하고 Conflict Marker를 제거한 뒤 Add, Commit, Push 순서로 완료합니다.

Q9. Push HEAD란 무엇인가요?

현재 HEAD가 가리키는 Local Branch의 최신 Commit History를 설정된 원격 Branch로 전송하는 EGit 작업입니다.

Q10. Push rejected를 Force Push로 해결하면 안 되는 이유는 무엇인가요?

Force Push는 원격 History를 Local 기준으로 강제로 변경하여 다른 팀원의 Commit을 잃게 만들 수 있기 때문입니다.

Q11. origin/main은 GitHub의 실시간 상태인가요?

아닙니다. 마지막 Fetch 또는 Pull 결과를 나타냅니다. 원격의 최신 상태를 확인하려면 다시 Fetch해야 합니다.

Q12. 실무에서는 Pull과 Fetch 중 무엇을 사용하나요?

간단한 작업에서는 Pull을 사용할 수 있습니다. 원격 변경을 먼저 검토해야 하는 팀 작업에서는 Fetch 후 History를 확인하고 Merge하는 방식을 사용할 수 있습니다.
