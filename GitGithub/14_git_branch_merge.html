Branch 생성과 Merge

하나의 main에서 모든 기능을 바로 개발하면 미완성 코드와 테스트 실패가 기준 Branch에 섞일 수 있습니다.
Git Branch를 사용하면 안정적인 main은 그대로 유지한 채, feature/login, feature/payment 같은 독립적인 작업선에서 기능을 개발할 수 있습니다.
기능 개발이 끝난 뒤에는 main으로 돌아와 기능 Branch의 Commit History를 Merge하고, Build와 Test를 거친 결과만 GitHub에 Push합니다.
이번 단원의 중심 질문은 “왜 main에서 모든 기능을 직접 개발하지 않고, 별도의 Branch에서 작업한 뒤 다시 Merge해야 할까?” 입니다.

왜 main에서 바로 개발하지 않는가?

main에서 직접 개발

기준 Branch가 불안정해짐

  • 미완성 기능이 main에 포함됩니다.
  • 컴파일 오류와 테스트 실패가 섞일 수 있습니다.
  • 실험 코드와 디버깅 코드가 기준 코드에 남습니다.
  • 기능을 폐기할 때 History 정리가 어려워집니다.
  • 다른 팀원의 작업과 충돌 범위가 커질 수 있습니다.
기능 Branch에서 개발

main과 기능 작업을 분리

  • main은 실행 가능한 기준 상태를 유지합니다.
  • 미완성 기능은 기능 Branch에만 존재합니다.
  • 기능별 Commit History를 분리할 수 있습니다.
  • 완성되지 않은 기능은 Merge하지 않을 수 있습니다.
  • Code Review와 테스트 범위를 명확히 할 수 있습니다.

03

Branch는 프로젝트 복사본이 아니라 포인터다

Branch를 만들 때 프로젝트 폴더 전체가 복사되는 것이 아닙니다. Branch는 특정 Commit을 가리키는 이름 있는 포인터입니다.

Branch 생성 전 
A ── B ── C
          ↑
         main

main이 최신 Commit C를 가리킵니다.

새 Branch 생성 →
Branch 생성 후 
A ── B ── C
          ↑
   main, feature/login

같은 Commit C를 가리키는 새로운 Branch 이름만 추가됩니다.

Commit 객체 공유

main과 feature/login은 기존 Commit과 파일 객체를 함께 사용합니다.

빠른 생성

프로젝트 전체를 복사하지 않으므로 Branch 생성 자체는 빠릅니다.

Branch별 새 Commit

Branch마다 달라진 작업은 새로운 Commit으로 추가됩니다.

이름 있는 작업선

Branch 이름을 통해 작업 목적과 현재 위치를 구분할 수 있습니다.

04

HEAD와 Branch의 이동

처음 상태 
A ── B ── C
          ↑
       HEAD → main

HEAD는 현재 작업 Branch인 main을 가리킵니다.

기능 Branch 전환 
A ── B ── C
          ↑
        main
          ↑
HEAD → feature/login

새 Commit이 없으므로 두 Branch는 같은 C를 가리킵니다.

기능 Commit 생성 
A ── B ── C ── D ── E
          ↑            ↑
        main     HEAD → feature/login

새로운 Commit D와 E는 feature/login에만 연결됩니다.

Commit이 추가되는 위치

HEAD → 현재 Branch → 새 Commit

현재 Branch가 main이면 main에 Commit이 추가되고, 현재 Branch가 feature/login이면 feature/login에 Commit이 추가됩니다.

작업 전에 현재 Branch를 확인합니다

06

Branch 생성과 전환은 다른 작업이다

CREATE ONLY

Branch만 생성

git branch feature/login

feature/login은 만들어지지만 현재 Branch와 HEAD는 main에 남습니다.

SWITCH ONLY

기존 Branch로 전환

git switch feature/login

이미 존재하는 feature/login으로 HEAD와 Working Directory를 이동합니다.

CREATE + SWITCH

생성과 전환을 한 번에

git switch -c feature/login

새 Branch를 만들고 바로 해당 Branch로 전환합니다.

기존에 널리 사용된 명령

git checkout -b feature/login

새 Branch 생성과 전환을 함께 수행합니다. 이번 교안에서는 의미가 더 명확한 git switch -c도 함께 연결합니다.

15

Fast-forward와 Merge Commit 비교

FAST-FORWARD

History가 직선으로 이어짐

A ── B ── C ── D ── E
                         ↑
                       main
  • main에 별도 Commit이 없을 때 가능합니다.
  • 새 Merge Commit을 만들지 않습니다.
  • History가 단순하게 보입니다.
  • 기능 Branch 통합 지점은 덜 명확할 수 있습니다.
MERGE COMMIT

Branch 통합 지점이 기록됨

          D ── E
         /      \
A ── B ── C      M
         \      /
          F ────
  • 양쪽 Branch가 각각 진행했을 때 만들어질 수 있습니다.
  • 두 개의 부모 Commit을 가집니다.
  • 기능 Branch 통합 지점이 History에 남습니다.
  • Merge가 많으면 Graph가 복잡해질 수 있습니다.

Merge Commit을 명시적으로 남기는 옵션

git merge --no-ff feature/login

이번 기본 실습에서는 일반 git merge feature/login을 사용합니다.

초보자가 자주 하는 실수

1. Branch를 폴더 복사본으로 생각

Branch는 프로젝트 전체 복사가 아니라 Commit 포인터입니다.

2. 현재 Branch를 확인하지 않음

기능 작업을 실수로 main에 Commit할 수 있습니다.

3. 오래된 main에서 Branch 생성

최신 Remote 변경이 빠져 나중에 Conflict가 커질 수 있습니다.

4. Branch만 만들고 전환하지 않음

git branch는 생성만 하고 HEAD를 이동하지 않습니다.

5. 잘못된 Start Point 사용

다른 기능 Branch의 Commit이 새 Branch에 포함될 수 있습니다.

6. 기능 Commit이 main에 자동 반영된다고 생각

main에 반영하려면 명시적인 Merge가 필요합니다.

7. Merge 방향을 반대로 실행

기능을 main에 넣으려면 main에서 feature Branch를 Merge합니다.

8. 미Commit 변경 상태에서 Switch

파일 손실 위험 때문에 Branch 전환이 거절될 수 있습니다.

9. 전환 후 파일이 삭제됐다고 오해

현재 Branch Commit에 없는 파일이 보이지 않는 것입니다.

10. Merge 결과 상태를 확인하지 않음

Fast-forward, Merge Commit, Conflict를 구분해야 합니다.

11. Merge 성공 후 테스트 생략

텍스트 통합 성공과 프로그램 정상 동작은 다릅니다.

12. Local Branch가 GitHub에도 자동 생성된다고 생각

Remote Branch는 Push해야 생성됩니다.

13. Merge 직후 강제 삭제

Build, Test와 main Push를 확인한 뒤 Branch를 삭제합니다.

14. Local과 Remote Branch를 동일하게 생각

feature/login과 origin/feature/login은 역할이 다릅니다.

15. 하나의 Branch에 모든 기능을 넣음

Review와 Merge가 가능한 작은 작업 단위로 나눕니다.

16. Detached HEAD에서 Commit

HEAD가 Branch가 아닌 Commit을 직접 가리키는지 확인합니다.

면접 포인트

Q1. Git Branch란 무엇인가요?

특정 Commit을 가리키는 이름 있는 이동 가능한 포인터입니다. 현재 Branch에서 Commit하면 해당 Branch가 새 Commit으로 이동합니다.

Q2. Branch를 만들면 프로젝트 폴더가 복사되나요?

아닙니다. Branch는 기존 Commit 객체를 공유하는 가벼운 참조이며, Branch 전환 시 Working Directory가 해당 Commit 상태로 변경됩니다.

Q3. HEAD란 무엇인가요?

현재 Checkout된 Branch 또는 Commit을 가리키는 포인터입니다. 일반적인 Branch 작업에서는 HEAD가 현재 Branch를 가리킵니다.

Q4. Branch 생성과 전환의 차이는 무엇인가요?

Branch 생성은 새로운 포인터를 만드는 작업이고, 전환은 HEAD와 Working Directory를 해당 Branch 상태로 이동시키는 작업입니다.

Q5. 기능 Branch를 main에 합치는 순서는 무엇인가요?

먼저 main으로 전환한 뒤 git merge feature/login을 실행합니다.

Q6. 왜 main으로 먼저 전환해야 하나요?

Merge 결과는 현재 Checkout된 Branch에 반영되기 때문입니다. 기능을 main에 넣으려면 main이 현재 Branch여야 합니다.

Q7. Fast-forward Merge란 무엇인가요?

현재 Branch가 병합 대상 Branch의 과거 Commit을 가리키고 있어 새 Merge Commit 없이 Branch 포인터만 앞으로 이동하는 Merge입니다.

Q8. Merge Commit은 언제 만들어지나요?

현재 Branch와 병합 대상 Branch가 공통 조상 이후 각각 다른 Commit을 가지고 있어 두 History를 통합할 때 만들어질 수 있습니다.

Q9. 기능 Branch에서 Commit하면 main도 바뀌나요?

아닙니다. Commit은 현재 HEAD가 연결된 기능 Branch에만 추가됩니다. main에 반영하려면 Merge가 필요합니다.

Q10. Local Branch를 만들면 GitHub에도 자동으로 생성되나요?

아닙니다. Remote Branch를 만들려면 git push -u origin feature/login처럼 Push해야 합니다.

Q11. Merge 후 기능 Branch는 자동 삭제되나요?

아닙니다. Merge와 Branch 삭제는 별도의 작업입니다. 검증 후 필요 없을 때 삭제합니다.

Q12. `git branch -d`와 `-D`의 차이는 무엇인가요?

`-d`는 Merge되지 않은 Commit이 있으면 삭제를 거절하는 안전 삭제이고, `-D`는 강제로 삭제합니다.

Q13. Branch 전환이 거절되는 이유는 무엇인가요?

미Commit 변경이 대상 Branch의 파일 상태로 인해 덮어써질 위험이 있으면 Git이 전환을 거절할 수 있습니다.

Q14. Pull Request와 Branch는 어떤 관계인가요?

Branch는 독립적인 작업선을 만드는 Git 기능이고, Pull Request는 기능 Branch 변경을 검토하고 대상 Branch에 통합하도록 요청하는 협업 기능입니다.

Q15. Detached HEAD란 무엇인가요?

HEAD가 Branch가 아니라 특정 Commit을 직접 가리키는 상태입니다. 이 상태의 Commit을 보관하려면 새 Branch를 만들어 연결해야 합니다.
