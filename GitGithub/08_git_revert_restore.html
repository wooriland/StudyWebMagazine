Git/GitHub - Chapter 08

Revert / Restore / Reset 비교

Git에는 하나의 Undo 버튼 대신 Restore, Revert, Reset이라는 서로 다른 되돌리기 도구가 있습니다.
세 명령은 되돌리는 대상과 History에 미치는 영향이 다르기 때문에, 파일 상태, Commit 여부, Push 여부를 먼저 확인한 뒤 선택해야 합니다.
이번 단원의 핵심 질문은 “되돌리려는 대상은 파일인가, Commit인가, Branch History인가?” 입니다.

Restore Revert Reset Working Directory Staging Area Index HEAD Commit ID History Tracked Untracked Replace With Revert Commit Conflict git revert --continue git revert --abort git restore --staged git restore --source Patch Shared History Force Push

정확하게 구분할 수 있습니다.

01

Git에 되돌리기 명령이 여러 개인 이유

Git은 단순히 현재 파일 하나만 관리하지 않습니다.
실제로 수정 중인 파일, 다음 Commit에 들어갈 상태, 이미 만들어진 Commit, Branch가 가리키는 History를 각각 따로 관리합니다.
따라서 “되돌린다”는 말도 무엇을 되돌리는지에 따라 의미가 달라집니다.

File

현재 파일을 되돌린다

아직 Commit하지 않은 Working Directory의
파일 내용을 복원합니다.

Stage

Stage 상태를 되돌린다

Add한 파일을 Staging Area에서 내리되
파일 수정 내용은 유지합니다.

Commit

Commit의 효과를 취소한다

특정 Commit이 만든 변경을 반대로 적용한
새로운 Commit을 만듭니다.

History

Branch History를 되돌린다

현재 Branch가 가리키는 Commit을
과거 Commit으로 이동합니다.

RESTORE

파일 또는 Index 복원

Commit 전 파일 실수와
잘못 Stage한 파일을 정리합니다.

REVERT

취소용 새 Commit 생성

이미 공유된 특정 Commit의 효과를
History를 보존하며 취소합니다.

RESET

Branch를 과거로 이동

아직 공유하지 않은 Local History를
과거 Commit부터 다시 구성합니다.

세 명령을 한 문장으로 구분하기

Restore는 파일을 복원하고, Revert는 Commit의 효과를 취소하며, Reset은 Branch의 위치를 바꿉니다.

02

어떤 명령을 선택해야 할까?

명령어보다 먼저 확인해야 하는 것은 Commit 여부와 공유 여부입니다.

질문 1

아직 Commit하지 않았는가?

Working Directory 또는 Staging Area의 문제라면 Restore를 먼저 검토합니다.

→
질문 2

이미 Commit했는가?

Commit을 만들었다면 Reset 또는 Revert 중에서 선택합니다.

→
질문 3

GitHub에 Push했는가?

이미 공유된 History라면 Revert를 우선 사용합니다.

파일 수정 취소

Commit 전

Add만 취소

Commit 후 · 공유됨

Commit 후 · 공유 전

git reset --mixed HEAD~1

파일 하나의 문제인가?

Restore를 먼저 검토합니다.

특정 Commit의 영향만 취소할 것인가?

Revert를 먼저 검토합니다.

Branch를 과거로 옮길 것인가?

Reset을 검토합니다.

팀원이 같은 History를 사용 중인가?

Reset보다 Revert가 안전합니다.

04

Restore — Commit 전 파일을 복원하기

git restore는 파일이나 Index를 Git이 알고 있는 기준 상태로 복원합니다.
현재 Branch와 HEAD는 이동하지 않으며, 새 Commit도 자동으로 만들지 않습니다.

History

Commit History 유지

Branch와 기존 Commit은 바뀌지 않습니다.

Worktree

파일 내용 복원

Working Directory 파일을
Index 또는 특정 Commit 상태로 바꿉니다.

Index

Stage 취소

잘못 Add한 파일을 Index에서 내리되
수정 내용은 유지할 수 있습니다.

Source

과거 버전 가져오기

Branch는 유지하고 특정 Commit의 파일만
현재 작업으로 가져올 수 있습니다.

Case 1

Stage하지 않은 수정 취소

HEAD      A
Index     A
Worktree  B

git restore file.html

HEAD      A
Index     A
Worktree  A
Case 2

Stage 이후 추가 수정 취소

HEAD      A
Index     B
Worktree  C

git restore file.html

HEAD      A
Index     B
Worktree  B
Case 3

삭제한 Tracked 파일 복원

파일 삭제
  ↓
git restore file.html
  ↓
Index 버전으로 복원

git restore 파일명은 무조건 HEAD 복원이 아니다

기본 형태의 git restore 파일명은 Working Directory를 Index의 파일 내용으로 복원합니다. HEAD 상태를 명확히 사용하려면 --source=HEAD를 지정할 수 있습니다.

05

Restore 옵션과 상태 변화

Restore는 --staged, --worktree, --source, --patch 옵션을 조합하여 복원 대상과 복원 원본을 결정합니다.

목적 명령어 결과
Working Directory 수정 취소 git restore 파일명 Working Directory를 Index 내용으로 복원합니다.
Add만 취소 git restore --staged 파일명 Index를 HEAD 상태로 복원하고 파일 수정은 유지합니다.
Stage와 파일 모두 취소 git restore --source=HEAD --staged --worktree 파일명 Index와 Working Directory 모두 HEAD 상태로 복원합니다.
과거 Commit 파일 가져오기 git restore --source=CommitID 파일명 Branch는 유지하고 해당 파일만 과거 버전으로 바꿉니다.
이전 Commit 파일 가져오기 git restore --source=HEAD~1 파일명 파일을 바로 이전 Commit 버전으로 바꿉니다.
일부 변경만 취소 git restore -p 파일명 Diff Hunk를 선택하여 일부만 복원합니다.
현재 폴더 전체 복원 git restore . 현재 폴더 아래 여러 Tracked 파일 변경을 복원합니다.
--staged

Stage만 취소

git restore --staged README.md

README 수정은 남아 있지만
Staged Changes에서 Unstaged Changes로 이동합니다.

--source

복원 원본 지정

git restore --source=a41c2e7 lesson.html

현재 Branch는 그대로 두고
lesson.html만 지정한 Commit 버전으로 가져옵니다.

--patch

일부 Hunk만 복원

git restore -p lesson.html

제목과 본문은 유지하고
임시 디버그 코드만 선택적으로 취소할 수 있습니다.

파일의 세 가지 변경

  • 제목 수정
  • 본문 설명 추가
  • 임시 디버그 로그 추가
Patch 선택

최종 결과

  • 제목 수정 유지
  • 본문 설명 유지
  • 디버그 로그만 Restore

Restore도 데이터 손실이 발생할 수 있다

Restore로 버린 미Commit 변경은 Commit History에 존재하지 않을 수 있습니다. 실행 전 git diff와 git diff --staged로 사라질 내용을 반드시 확인합니다.

07

Revert — Commit의 효과를 취소하는 새 Commit

Revert는 과거 Commit을 삭제하지 않습니다. 대상 Commit이 만들었던 변경을 반대로 적용하고, 그 결과를 새로운 Commit으로 기록합니다.

A

Initial project

B

Add login button

Revert 대상
C

Update login style

R

Revert "Add login button"

새 Commit
Keep

원본 Commit 유지

취소 대상 Commit은
History에서 삭제되지 않습니다.

Inverse

반대 변경 적용

대상 Commit의 Patch를
반대 방향으로 적용합니다.

New Commit

취소용 Commit 생성

취소 사실이 새로운 Commit으로 기록됩니다.

Shared

공유 History에 적합

기존 Commit 연결을 유지하므로
팀 작업에 안전합니다.

최신 Commit C를 Revert

전
A → B → C

git revert HEAD

후
A → B → C → Revert-C

파일 상태는 B와 비슷해질 수 있지만 C와 Revert-C가 모두 History에 남습니다.

중간 Commit B를 Revert

전
A → B → C → D

git revert B

후
A → B → C → D → Revert-B

C와 D는 유지하면서 B의 효과만 취소하려고 시도합니다.

Revert의 핵심

Revert는 과거로 이동하는 기능이 아니라, 현재 History 위에 취소 사실을 기록하는 기능입니다.

Revert Conflict는 왜 발생할까?

중간 Commit이 만든 코드를 이후 Commit이 다시 수정하거나 사용했다면, 과거 Commit의 변경만 분리해 취소하기 어려울 수 있습니다.

Commit B

로그인 버튼 추가

화면에 로그인 버튼을 처음 만듭니다.

→
Commit C

버튼 색상 변경

B에서 만든 버튼의 스타일을 수정합니다.

→
Commit D

클릭 이벤트 추가

B에서 만든 버튼에 JavaScript 동작을 연결합니다.

이 상태에서 Commit B를 Revert한다면?

버튼을 완전히 삭제할 것인가? C의 색상 코드는 어떻게 처리할 것인가? D의 클릭 이벤트는 유지할 것인가?

10

Revert 명령어와 진행 상태 관리

기본 Revert 외에도 Commit Message 편집 여부, 자동 Commit 여부, Conflict 진행 상태를 제어하는 옵션이 있습니다.

목적 명령어 의미
특정 Commit Revert git revert CommitID 반대 변경을 적용한 새 Commit을 생성합니다.
최신 Commit Revert git revert HEAD 현재 HEAD Commit의 효과를 취소합니다.
Message 편집 생략 git revert --no-edit CommitID Git의 기본 Revert Message를 그대로 사용합니다.
자동 Commit 생략 git revert --no-commit CommitID 반대 변경만 Index와 Working Directory에 적용합니다.
Conflict 해결 후 계속 git revert --continue 해결된 파일을 기준으로 Revert를 완료합니다.
진행 중 Revert 취소 git revert --abort Revert 시작 전 상태로 돌아갑니다.
현재 항목 건너뛰기 git revert --skip 여러 Commit Revert에서 현재 Commit을 건너뜁니다.
Sequencer 종료 git revert --quit 진행 정보를 종료하고 현재 파일 상태는 남길 수 있습니다.
--no-edit

기본 Message 사용

git revert --no-edit a41c2e7

편집기를 열지 않고 Git이 만든 기본 Message로 Revert Commit을 생성합니다.

--no-commit

변경을 먼저 검토

git revert --no-commit a41c2e7

git status
git diff --staged

반대 변경을 확인하고 테스트한 뒤 직접 Commit할 수 있습니다.

--abort

Revert 취소

git revert --abort

Conflict 해결을 포기하거나 대상 Commit을

일반 Commit은 Parent가 하나지만, Merge Commit은 둘 이상의 Parent를 가질 수 있습니다. 따라서 어느 Parent를 기준선으로 삼을지 지정해야 합니다.

      \               /
       D ── E ───────

Mainline

일반적으로 Merge를 받은 현재 Branch의 흐름입니다.

Parent 2

Merged Branch

기능 개발 Branch의 흐름일 수 있습니다.

Merge Commit Revert 예시

git show --summary MergeCommitID

git revert -m 1 MergeCommitID

초보 단계에서는 임의로 실행하지 않는다

Merge Commit Revert는 이후 같은 Branch를 다시 Merge할 때 Git이 어떤 변경을 이미 처리한 것으로 판단하는지에도 영향을 줄 수 있습니다.

git rm과 Restore의 차이

rm과 restore는 모두 파일을 대상으로 하지만 목적이 반대입니다. rm은 삭제를 Git 변경으로 만들고, restore는 Git이 알고 있는 상태로 파일을 복원합니다.

git rm

파일 삭제를 Commit 대상으로 등록

git rm old-file.txt

git commit -m "Remove obsolete file"

Working Directory와 Index에서 파일을 제거하고
다음 Commit에 삭제 변경을 포함합니다.

git rm --cached

파일은 남기고 추적만 중단

git rm --cached config.local

Working Directory 파일은 유지하고
Index와 Git 추적 대상에서 제외합니다.

git restore

파일 변경을 복원

git restore old-file.txt

삭제 변경을 만드는 것이 아니라
Git이 알고 있는 파일 상태로 복원합니다.

rm과 restore 암기

git rm은 삭제를 기록하고, git restore는 파일 상태를 되돌립니다.

면접 포인트

Q1. Restore, Revert, Reset의 차이는 무엇인가요?

Restore는 파일이나 Index를 복원하며 Branch를 이동하지 않습니다. Revert는 특정 Commit의 변경을 취소하는 새 Commit을 만듭니다. Reset은 현재 Branch가 가리키는 Commit을 이동시켜 History를 변경할 수 있습니다.

Q2. git restore 파일명은 어디에서 파일을 가져오나요?

별도의 Source와 --staged를 지정하지 않은 기본 형태에서는 Index의 내용을 Working Directory에 복원합니다.

Q3. git restore --staged 파일명은 무엇을 하나요?

Index를 기본적으로 HEAD 상태로 복원하여 Stage를 취소합니다. Working Directory의 파일 수정은 유지됩니다.

Q4. Stage와 파일 변경을 모두 취소하려면 어떻게 하나요?

git restore --source=HEAD --staged --worktree 파일명을 사용할 수 있습니다. Index와 Working Directory가 모두 HEAD 상태로 복원됩니다.

Q5. 특정 Commit의 파일 하나만 가져오려면 어떻게 하나요?

git restore --source=CommitID 파일명을 사용합니다. 현재 Branch는 이동하지 않고 해당 파일만 지정한 Commit 버전으로 바뀝니다.

Q6. git restore -p는 무엇인가요?

파일 전체가 아니라 Diff Hunk를 하나씩 확인하며 일부 변경만 선택적으로 Restore하는 Patch 모드입니다.

Q7. Untracked 파일도 Restore할 수 있나요?

한 번도 Add하거나 Commit하지 않은 파일은 Git이 알고 있는 복원 원본이 없으므로 일반적으로 Restore할 수 없습니다.

Q8. Revert란 무엇인가요?

특정 Commit이 도입한 변경을 반대로 적용하고 그 결과를 새로운 Commit으로 기록하는 명령입니다.

Q9. Revert하면 대상 Commit이 삭제되나요?

아닙니다. 대상 Commit은 History에 그대로 남고 취소용 Revert Commit이 추가됩니다.

Q10. Revert하면 Branch가 과거로 이동하나요?

아닙니다. 현재 HEAD 위에 새 Revert Commit이 만들어지므로 Branch는 앞으로 이동합니다.

Q11. Reset과 Revert의 대상 선택 기준은 어떻게 다른가요?

Reset에서는 이동 후 남길 마지막 Commit을 선택하고, Revert에서는 실제 변경을 취소할 Commit을 선택합니다.

Q12. 중간 Commit만 취소하려면 무엇을 사용하나요?

Revert를 사용합니다. 이후 Commit을 유지하면서 대상 Commit의 효과만 취소하는 새 Commit을 만듭니다.

Q13. Revert Conflict가 발생하는 이유는 무엇인가요?

취소할 Commit의 코드가 이후 Commit에서 다시 수정되었거나, 이후 변경이 그 코드에 의존하여 Git이 자동으로 반대 Patch를 적용하기 어렵기 때문입니다.

Q14. Revert Conflict는 어떻게 해결하나요?

최종 코드를 직접 작성하고 Conflict Marker를 제거한 뒤 git add와 git revert --continue를 실행합니다.

Q15. 진행 중 Revert를 취소하려면 어떻게 하나요?

git revert --abort를 사용하여 Revert 시작 전 상태로 돌아갑니다.

Q16. git revert --no-edit은 무엇인가요?

Git이 생성한 기본 Revert Commit Message를 별도 편집 없이 그대로 사용하는 옵션입니다.

Q17. git revert --no-commit은 무엇인가요?

반대 변경을 Index와 Working Directory에 적용하지만 Revert Commit은 자동으로 만들지 않는 옵션입니다.

Q18. Revert Commit을 다시 Revert하면 어떻게 되나요?

첫 번째 Revert의 효과를 취소하므로 원래 Commit의 변경이 다시 적용되는 효과가 날 수 있습니다.

Q19. Merge Commit Revert에 -m 옵션이 필요한 이유는 무엇인가요?

Merge Commit은 Parent가 둘 이상이므로 어느 Parent를 Mainline으로 볼지 지정해야 하기 때문입니다.

Q20. Push된 Commit에는 왜 Revert가 적합한가요?

기존 History를 삭제하지 않고 취소용 새 Commit을 추가하므로 Remote와 팀원이 가진 History 연결을 유지할 수 있습니다.

Q21. Revert는 항상 Conflict 없이 안전한가요?

아닙니다. History 보존 측면에서는 안전하지만 코드 의존성과 이후 수정 때문에 Conflict가 발생할 수 있습니다.

Q22. Reset은 언제 사용하는 것이 적절한가요?

아직 Push하지 않은 개인 Local Commit을 다시 구성하거나 최근 Commit을 합치고 나눌 때 사용합니다.

Q23. Hard Reset의 위험은 무엇인가요?

HEAD, Index, Working Directory를 모두 대상 Commit 상태로 맞추므로 미Commit 추적 파일 변경까지 잃을 수 있습니다.

Q24. git rm과 git restore의 차이는 무엇인가요?

git rm은 파일 삭제를 Git 변경으로 만들고, git restore는 파일을 Git이 알고 있는 상태로 복원합니다.

Q25. Eclipse에서 Restore에 해당하는 기능은 무엇인가요?

주로 파일 우클릭 후 Replace With 메뉴를 사용합니다. File in Git Index, HEAD, Commit, Branch·Tag·Reference 등을 선택할 수 있습니다.

Q26. Eclipse에서 Revert는 어떻게 실행하나요?

Team → Show In History에서 실제 취소할 Commit을 선택한 뒤 Revert Commit을 실행합니다.

Q27. 같은 파일 상태여도 Reset과 Revert가 다른 이유는 무엇인가요?

Reset은 Branch History를 과거로 이동시키고, Revert는 기존 Commit과 취소 사실을 모두 History에 남기기 때문입니다.

헷갈리기 쉬운 개념

Restore vs Revert

Restore는 파일, Revert는 Commit의 효과를 대상으로 합니다.

Revert vs Reset

Revert는 새 Commit을 만들고, Reset은 Branch를 과거로 이동합니다.

restore vs restore --staged

기본 Restore는 파일을 복원하고, --staged는 Add 상태를 취소합니다.

Reset 대상 vs Revert 대상

Reset은 남길 Commit, Revert는 실제 취소할 Commit을 선택합니다.

파일 상태 vs History

파일 내용이 같아도 Reset과 Revert History는 다릅니다.

Tracked vs Untracked

Git이 추적한 적 없는 파일은 Restore 원본이 없습니다.

Conflict 해결 vs 완료

파일 수정 후 Add와 Revert Continue까지 해야 완료됩니다.

Revert Abort vs Hard Reset

진행 중 Revert 취소에는 먼저 --abort를 사용합니다.

rm --cached vs Unstage

rm --cached는 추적 중단, restore --staged는 이번 Stage만 취소합니다.
