04

자동 Merge와 Conflict의 경계

AUTO MERGE

서로 다른 파일 수정

Local: local-note.txt Remote: remote-note.txt

두 변경을 모두 적용할 수 있으므로 Git이 자동으로 합칠 수 있습니다.

AUTO MERGE

같은 파일의 다른 줄 수정

Local  : 1번 줄 수정
Remote : 3번 줄 수정

수정 영역이 충분히 떨어져 있다면 Git이 양쪽 변경을 모두 반영할 수 있습니다.

CONFLICT

같은 파일의 같은 줄 수정

Local  : 제목을 Git Merge로 수정
Remote : 제목을 GitHub 협업으로 수정

같은 위치에 서로 다른 결과가 요구되어 자동 판단이 불가능합니다.

CONFLICT

같은 위치에 서로 다른 내용 추가

Local  : Merge 항목 추가
Remote : Pull 항목 추가

내용의 순서와 최종 구성을 사람이 결정해야 할 수 있습니다.

판단 기준

Git이 두 변경을 모두 적용한 하나의 결과를 계산할 수 있으면 자동 Merge하고, 같은 영역에 경쟁하는 결과가 있으면 Conflict로 멈춥니다.

07

Conflict 해결의 네 가지 선택

LOCAL ONLY

Local만 유지

오늘의 학습 주제는 Git Merge입니다.

Remote 변경을 최종 파일에서 제외합니다.

REMOTE ONLY

Remote만 유지

오늘의 학습 주제는 GitHub 협업입니다.

Local 변경을 최종 파일에서 제외합니다.

KEEP BOTH

두 내용 모두 유지

오늘의 학습 주제는 Git Merge입니다.
두 번째 주제는 GitHub 협업입니다.

두 변경이 독립적으로 모두 필요할 때 사용합니다.

REWRITE

새로운 결과로 재작성

오늘의 학습 주제는
Git Merge와 GitHub 협업입니다.

양쪽 의도를 분석하여 가장 적합한 최종 결과를 만듭니다.

실무의 핵심

Conflict 해결은 Local 또는 Remote 버튼을 기계적으로 고르는 작업이 아니라, 양쪽 변경의 이유와 프로젝트 요구사항을 이해해 올바른 결과를 만드는 작업입니다.

초보자가 자주 하는 실수

1. Conflict를 프로젝트 손상으로 생각

Conflict는 자동 판단이 멈춘 정상적인 Git 상태입니다.

2. Local을 무조건 정답으로 선택

Remote에는 중요한 버그 수정과 팀 합의가 있을 수 있습니다.

3. Remote를 무조건 최신 정답으로 선택

시간상 최신 Commit이 업무상 정답이라는 보장은 없습니다.

4. Marker만 삭제하고 코드 검토 생략

중복 코드, 누락 코드와 문법 오류가 남을 수 있습니다.

5. 파일 저장 후 Add하지 않음

Git은 Add 전까지 해결 완료로 인식하지 않을 수 있습니다.

6. 일부 Conflict 파일만 해결

git status에서 모든 Unmerged Paths를 확인해야 합니다.

7. Add 후 Commit하지 않음

Add는 Stage이며 Merge 완료에는 Commit이 필요합니다.

8. Merge 중 다시 Pull 실행

현재 Merge를 먼저 완료하거나 중단해야 합니다.

9. Force Push로 Conflict 해결 시도

파일 내용은 해결되지 않고 원격 History만 위험해집니다.

10. 자동 Merge 후 테스트 생략

텍스트 통합 성공과 프로그램 동작 성공은 다릅니다.

11. Merge Tool 방향을 확인하지 않음

Local과 Incoming 영역을 반대로 덮어쓸 수 있습니다.

12. Binary 파일을 텍스트처럼 해결

한쪽을 선택하거나 원본 편집 도구를 사용해야 합니다.

면접 포인트

Q1. Git Conflict란 무엇인가요?

두 Branch의 변경을 통합하는 과정에서 Git이 최종 파일 내용을 자동으로 결정할 수 없어 개발자의 수동 판단이 필요한 상태입니다.

Q2. 같은 파일을 수정하면 항상 Conflict가 발생하나요?

아닙니다. 같은 파일이라도 서로 다른 줄이나 겹치지 않는 영역을 수정했다면 Git이 자동으로 Merge할 수 있습니다.

Q3. Push rejected와 Conflict의 차이는 무엇인가요?

Push rejected는 원격에 Local이 모르는 Commit이 있어 Push가 거절된 상태입니다. Conflict는 원격 변경을 통합하는 과정에서 최종 파일 내용을 결정하지 못한 상태입니다.

Q4. Base, Ours, Theirs는 무엇인가요?

Base는 공통 조상, Ours는 현재 Checkout된 Branch, Theirs는 현재 Branch에 합치려는 병합 대상의 내용입니다.

Q5. `<<<<<<< HEAD`는 무엇을 의미하나요?

현재 Checkout된 Branch의 충돌 내용이 시작되는 지점입니다.

Q6. `=======`는 무엇인가요?

현재 Branch 내용과 병합 대상 Branch 내용을 구분하는 경계입니다.

Q7. Conflict 해결의 기본 순서는 무엇인가요?

충돌 파일을 수정하고 Marker를 제거한 뒤 저장, Add, Commit, Test, Push 순서로 완료합니다.

Q8. 파일 수정 후 왜 git add가 필요한가요?

Git에게 해당 파일의 Conflict가 해결되었고, 현재 내용을 최종 Merge 결과로 사용하겠다고 알리기 위해 필요합니다.

Q9. Merge Commit이란 무엇인가요?

서로 갈라진 두 Branch의 History를 통합한 결과를 기록하는 Commit이며, 일반적으로 두 개의 부모 Commit을 가집니다.

Q10. Merge를 취소하려면 어떻게 하나요?

Merge 진행 중에는 git merge --abort를 사용해 가능한 한 Merge 시작 전 상태로 돌아갈 수 있습니다.

Q11. 자동 Merge가 성공하면 테스트가 필요 없나요?

필요합니다. Git은 텍스트를 합칠 뿐, 코드의 문법과 비즈니스 로직을 검증하지 않습니다.

Q12. Conflict를 줄이는 방법은 무엇인가요?

작업 시작 전 최신 변경을 가져오고, 기능별 Branch와 작은 Commit을 사용하며, 공통 파일 수정과 대규모 리팩터링을 팀에 공유합니다.
